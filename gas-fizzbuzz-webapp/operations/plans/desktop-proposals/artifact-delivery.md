# Windows配布artifactの受渡し調査

2026-10-14。現在のALL_TOOLSのname/descriptionを調査した。一般ファイルupload、公開artifact作成、File Service書込のcallable toolはない。Sediment download_fileはユーザー添付のdownload専用で、workspaceで生成したZIPをuploadできない。image_genやview_imageは任意ZIPの配布に使えない。ローカルfileリンクのレンダリングはサポートされるが、150MB以上のworkspaceファイルをユーザーが直接downloadできる機能があるとtool metadataからは確認できない。

生成exe/ZIPは /workspace/val-desktop-setup またはrepo内無追跡artifactsへ保存し、repo mainにruntimeの大きいバイナリをcommitしない。今回のWindows公式ZIP自体が157,867,015bytesなので通常Gitの100MB単一ファイル制限を超える。配布はゲームsourceと固定版build scriptをmainへ入れたうえで別artifactとする。

利用可能候補:

1. GitHub Actions artifact。mainに保存するWindows build workflowで公式runtime取得/SHA確認→package→ZIP→actions/upload-artifact。ユーザーは実際に成功したrunのArtifactsからZIPをdownloadする。GitHubReleaseを公開する操作ではなく、workflowの既存main保存権限の範囲とruntime buildの承認後に進められる。artifactにはretention-daysを明示する。ログイン/リポジトリアクセスが必要な場合がある。run/artifactの実URLを取得してから渡し、仮URLを完成リンクとして表示しない。今回まだこのworkflowはrepoへ作成していない。
2. クライアント側workspace artifact downloadが提供される場合。任意ZIP uploadツールは現時点でないので、rootの最終出力で絶対パスを示すだけで「download可能」とは断定しない。別途UI機能が確認できれば保存artifactを添付として渡せる。
3. ユーザー承認済みの専用配布先。GitHub Releases/クラウド共有等は公開・外部書込となるため、その指示が出るまで新規公開しない。現在は実行していない。

Windows sourceのmain統合とWindows配布artifact完成/実機検証は別のゲート。Linuxからexeが作れたこと、artifactがdownloadできたこと、Win10/11で起動成功したことをそれぞれ分けて報告する。
