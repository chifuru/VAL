# VALIS Summary Manifest v1.0

---

## 0. 位置づけ

VALIS は、仕様書でもプログラムでもない。  
VALIS は、**自然言語で与えられた上位意図を、機能・実装・検証可能な形へ段階的に具体化するための中間言語構造**である。

VALIS は、単なる構文木ではなく、**意味階層ネットワーク構造**として扱う。

その本質は以下にある。

- 上位が自然言語に近く、下位が機械的構造に近い
- 意味の曖昧さを階層分解の過程で局所吸収する
- 仕様と機能を安定核として保持する
- 実装とコーディングの往還によって修正を吸収する
- 実装のうち意味保存に必須な中核要素のみ固定し、それ以外は可変とする
- 検証は別層で扱う
- 実行計画は本体に含めず、必要に応じて別ファイルとして管理する

---

## 1. VALIS の定義

VALIS とは、  
**自然言語で表された上位意図を、仕様・機能・実装・検証可能な単位へ段階的に具体化し、**  
**その意味を保持したまま読解・修正・再生成可能にする意味階層ネットワーク構造**である。

VALIS は次を実現する。

- 意味の局所化
- 上位制約の伝播
- 修正の末端化
- 実装の再生成
- 検証計画の導出
- 人間と AI の協調読解
- 安定核と可変部の分離

---

## 2. 基本原則

### 2.1 中間言語の役割

VALIS は、以下の中間媒体である。

- 仕様の意味を責務単位へ編成する
- 上位意図を下位へ伝播・具体化する
- 実装可能な単位へ落とし込む
- 検証対象を導出可能にする
- 変更差分を局所化する
- AI と人間の双方が読解・編集可能である

### 2.2 安定性の原則

VALIS では、すべての層を同じ変更容易性で扱わない。  
上位ほど安定し、下位ほど可変である。

---

## 3. 安定核と可変末端

VALIS における安定性の原則は以下とする。

- **仕様** は原則として不動
- **機能** は原則として不動
- **実装** は中核要素と可変要素に分かれる
- **コーディング** は可変末端として扱う
- 修正の主戦場は **実装〜コーディング** 間の往還に置く

仕様・機能を直接変更する場合は、単なる修正ではなく、上位構造への変更提案として扱う。

---

## 4. 実装中核要素

### 4.1 実装中核

実装のうち、以下に関わるものは **中核実装要素** とする。

- 認証・認可
- 状態遷移の中核
- 整合性維持条件
- 境界条件チェック
- 例外優先順位
- 外部副作用の発火条件
- 上位制約の具体化に直結する実装責務

中核実装要素は、自由変更対象としない。  
変更には提案・レビュー・承認を必要とする。

### 4.2 実装可変部

以下は原則として可変とする。

- コード分割
- 命名
- 局所最適化
- 補助処理
- UI の具体表現
- 実装上の細かな組み立て
- コーディング技法上の差し替え

## 5. 記述規則

### 5.1 ノード形式

各ノードは次の形式で記述する。

```text
ID:（参照元1, 参照元2 / ノード名）［状態］
	構成（要素・関係）:
	ノードを構成する要素、および要素間の関係を記述する。

	ロジック:
	構成がどのように解釈・展開・作用するかを記述する。

	実態:
	ロジックの作用によって成立する状態・構造を記述する。
```

### 5.2 ID階層

ノード ID は `.` によって主所属上の階層を表す。

ID階層は、ノードの正式な配置階層である。

```text
A1:
	最上位ノード。

A1.1:
	A1 の下位ノード。

A1.1.1:
	A1.1 の下位ノード。
```

親ノードは、ID の末尾要素を取り除いた ID によって一意に決定する。

```text
A1.1 の親:
	A1

A1.1.1 の親:
	A1.1

B1.2.1 の親:
	B1.2
```

`.` を含まない ID は、その層または系列における起点ノードとして扱う。

```text
A1
B1
C1
D1
E1
```

これらは、ID階層上は互いの親子ではない。

A/B/C/D/E の具体化関係、検証関係、依存関係、制約関係は、ID階層ではなく、括弧内参照元および Node File の詳細記録によって表す。

タブによるインデントは、ID階層を視覚的に表すために用いる。

したがって、タブの深さは ID階層と一致しなければならない。

```text
正:
A1
	A1.1

B1
	B1.1
		B1.1.1

C1
	C1.0
	C1.1

D1

E1
```

参照関係、意味的依存、制約、由来、検証対象、実装対象、接合対象は、タブの深さを変更しない。

ID階層とインデントが一致しない場合は、ID階層を正とし、インデントを修正する。

同一親を持つ子ノードの並び順は、必要に応じて読解順、重要度、評価順序に基づいて整理できる。

ただし、並び順は親子関係を変更しない。

### 5.3 ID と参照元の意味

ID階層と括弧内参照元は、異なる役割を持つ。

```text
ID階層:
	ノードの主所属と正式な配置階層を表す。

括弧内参照元:
	ノードの意味的依存、制約、由来、検証対象、実装対象、接合対象、証跡起点を表す。
```

ノードの主所属は、ID階層によって一意に決定する。

括弧内参照元は、主所属を変更しない。

参照されたノードは、自身の ID階層に基づく位置に残る。

意味接続のみを括弧内参照元で表す。

例えば、`C1` が `B1.1` を実装対象とする場合でも、`C1` は `B1.1` の下位ノードにはならない。

```text
正:
B1
	B1.1

C1:（B1.1 / 実装）
```

この場合、`C1` の主所属は `C1` であり、`B1.1` との関係は括弧内参照元による意味接続である。

同様に、`D1` が `C1` と `B1.1` を検証対象とする場合でも、`D1` は `C1` の下位ノードにはならない。

```text
正:
C1

D1:（C1, B1.1 / 検証計画）
```

この場合、`D1` の主所属は `D1` であり、`C1` および `B1.1` との関係は検証対象としての参照である。

参照関係は、読解、影響範囲探索、検証計画生成、検証証跡記録、状態変更理由、処理フラグの起点として利用できる。

ただし、参照関係によって ID階層または配置階層を変更してはならない。

### 5.4 参照種別

括弧内参照元および Node File の参照情報は、参照種別を持つことができる。

参照種別は、親子関係を変更しない。

```text id="manifest_reference_types"
主所属:
	ID階層によって決まる正式な配置関係。

意味依存:
	対象ノードの意味が、参照元ノードの意味に依存する関係。

制約由来:
	対象ノードが満たすべき制約の由来となる関係。

実装対象:
	C層ノードが実装する A/B ノードとの関係。

検証対象:
	D層またはE層ノードが検証対象とする A/B/C ノードとの関係。

証跡起点:
	状態変更案または処理フラグの根拠となる E 層証跡との関係。

接合対象:
	複数ノードを統合、調停、接続、優先順位整理する関係。

影響対象:
	変更、反例、制約競合、状態変更によって影響を受ける可能性がある関係。
```

Summary Manifest の括弧内参照元には、必要最小限の参照元を記載する。

参照種別の詳細は、原則として Node File に記録する。

Summary Manifest に参照種別を要約する場合は、読解経路、影響範囲探索、検証対象、処理フラグ判断に必要な範囲に限定する。

### 5.5 制約種別と制約競合

制約は、最低限以下に分類する。

```text id="manifest_constraint_types"
強制制約:
	ユーザー指示より優先され、満たせない場合は確定・反映できない制約。

通常制約:
	原則として満たす必要があるが、条件付きで保留、確認、上位変更提案にできる制約。

推奨条件:
	満たすことが望ましいが、満たせないだけでは即時に却下しない条件。
```

制約競合とは、複数の制約、参照、状態、ユーザー指示が同時に成立しない可能性をいう。

制約競合は、即時に一方を削除または上書きしない。

制約競合がある場合は、競合内容、関連ノード、制約種別、参照種別、優先順位、次フロー候補を記録する。

制約競合を機械的に解決できない場合は、人間確認事項または上位変更提案候補として扱う。


### 5.6 E 層証跡IDと対象バージョン

E 層証跡IDは、E 層検証証跡ノードを識別する ID である。

E 層証跡IDは、Summary Manifest の ID階層規則に従う。

```text id="manifest_evidence_id_rule"
E1:
	E 層における起点証跡ノード。

E1.1:
	E1 の下位に属する個別証跡、再検証証跡、または観点別証跡。

E2:
	E1 とは別系列の証跡ノード。
```

E 層証跡IDは、外部テストレポートID、ログID、CIジョブID、検証結果IDとは区別する。

```text id="manifest_evidence_id_distinction"
E層証跡ID:
	VALIS の E 層 Node File および Summary Manifest 上で証跡ノードを識別するID。

検証結果ID:
	取得または受領した外部結果、実行結果、ログ、テストレポートを識別するID。

実行対象バージョン:
	検証を実行したコード、成果物、設定、環境、画面、API、ビルド、コミット、データセットなどを再識別する情報。
```

E 層証跡ノードは、対応する D 層検証計画ID、検証対象ノードID、実行対象バージョンを保持する。

```text id="manifest_evidence_node_format"
E1.1:（D1, C1, B1.1 / 検証証跡名）［状態］
```

この場合、`E1.1` の主所属は E 層である。

`D1`、`C1`、`B1.1` は親ノードではなく、検証計画および検証対象としての参照元である。

実行対象バージョンは、VALIS ファイルの変更履歴を表すものではない。

実行対象バージョンは、検証がどの外部対象または実行対象に対して成立したかを示す証跡条件である。

対象バージョンが変わった場合、既存の E 層証跡は自動的に現在有効とは扱わない。

対象バージョン変更により証跡の有効性が失われる可能性がある場合は、証跡の無効化条件、再検証要否、検証計画更新要否、状態変更案、または次フロー候補として扱う。

## 6. 状態管理

### 6.1 状態

ノードには状態を与える。  
最低限、以下の状態を扱う。

- `草案`
- `提案中`
- `レビュー中`
- `承認済み`
- `差戻し`
- `凍結`
- `廃止`

### 6.2 状態の原則

- `承認済み` ノードを正式な生成基準とする
- `提案中` および `レビュー中` ノードは検討対象であり、正式基準ではない
- `差戻し` ノードは修正対象または注意対象として扱う
- `凍結` ノードは変更不可
- `廃止` ノードは参照可能だが、生成対象から除外する

状態は、ノードの現在の扱いを示す。  
状態は、次に実行すべき処理そのものを示すものではない。

### 6.3 状態と処理フラグ

状態と処理フラグは分離して扱う。

状態は、ノードの現在の扱いを示す。  
処理フラグは、当該ノードまたは関連ノードに対して次に必要な処理を示す。

状態は、ノード見出しの `［状態］` に記載する。  
処理フラグは、原則としてノード本体ファイルに詳細を記録する。

Summary Manifest には、必要に応じて処理フラグの要約のみを記載する。

処理フラグとして、最低限以下を扱う。

```text
修正要否:
	あり / なし / 確認必要

影響範囲探索要否:
	あり / なし / 確認必要

検証計画更新要否:
	あり / なし / 確認必要

再検証要否:
	あり / なし / 確認必要

上位変更提案要否:
	あり / なし / 確認必要

状態遷移要否:
	あり / なし

次フロー候補:
	FLOW番号またはFLOW名
```

処理フラグは状態ではない。  
したがって、`修正必要`、`再検証必要`、`影響範囲探索必要`、`承認候補`、`検証済み候補` などを状態名として扱わない。

これらは、処理フラグ、状態変更案、または次フロー候補として扱う。

### 6.3.1 処理フラグ要約と処理フラグインスタンス

処理フラグ要約と処理フラグインスタンスは分離して扱う。

```text id="manifest_flag_instance_separation"
処理フラグ要約:
	Summary Manifest に記載する、現在必要な処理の要約。

処理フラグインスタンス:
	発生原因単位で Node File に詳細記録する、個別の処理フラグ。
```

同じ対象ノードに同じ種類の処理フラグが複数発生する場合でも、発生原因、起点、証跡、解消条件が異なる場合は、別の処理フラグインスタンスとして扱う。

処理フラグインスタンスには、必要に応じて以下を含める。

```text id="manifest_flag_instance_fields"
処理フラグID
対象ノード
処理フラグ種別
処理フラグ値
起点種別
起点ノード
起点証跡
発生理由
発生FLOW
関連参照種別
関連制約
解消条件
解消候補
残存理由
次フロー候補
現在の扱い
```

Summary Manifest には、処理フラグインスタンスの全文を記載しない。

Summary Manifest には、後続 FLOW が読み込み判断を行うために必要な処理フラグ要約のみを記載する。

処理フラグインスタンスの詳細は、対象 Node File、または起点となる E 層 Node File に記録する。

### 6.4 状態変更案

各 FLOW は、必要に応じて状態変更案を作成できる。

状態変更案は、即時の状態変更ではない。  
状態変更案は、FLOW-09 状態遷移フローで確認・確定される。

状態変更案には、以下を含める。

- 対象ノード
- 現在の状態
- 変更後の状態候補
- 状態変更の理由
- 起点となる入力、変更、検証結果、または証跡
- 関連する処理フラグ
- 次フロー候補
- 承認要否

状態変更案が存在する場合でも、FLOW-09 状態遷移フローで確定されるまでは、対象ノードの状態を自動変更しない。

### 6.5 状態変更理由

状態変更が発生する場合は、状態変更理由を記録する。

状態変更理由には、必要に応じて以下を含める。

- 状態変更の起点
- 起点となるノード
- 起点となる検証証跡
- 状態変更の理由
- 修正要否
- 影響範囲探索要否
- 再検証要否
- 上位変更提案要否
- 次フロー候補
- 人間の確認または承認の要否

Summary Manifest には、状態変更理由の要約のみを記載する。  
詳細は、対象 Node File、または起点となる E 層 Node File に記録する。

### 6.6 検証証跡による状態変更

E 層の検証証跡により、対象ノードの状態変更案が発生する場合がある。

検証証跡は、対象ノードを直接修正しない。  
検証証跡は、検証結果に基づいて、修正要否、原因層候補、修正対象ノード候補、状態変更案、次フロー候補を記録する。

検証結果による状態変更案の目安は以下とする。

```text
成功:
	承認提案または検証済みフラグ候補として扱う。

失敗:
	修正要否を「あり」とし、対象ノードを差戻し候補として扱う。
	原因層が明確でない場合は、影響範囲探索要否を「あり」または「確認必要」とする。

部分成功:
	修正要否を「確認必要」とし、対象ノードをレビュー中候補または差戻し候補として扱う。

未確認:
	修正要否を「確認必要」とし、対象ノードをレビュー中候補または検証継続候補として扱う。

反例:
	修正要否を「あり」とし、対象ノードを差戻し候補として扱う。
	影響範囲探索要否を原則として「あり」とする。

証跡不備:
	E 層証跡自体をレビュー中候補または差戻し候補として扱う。
```

検証証跡によって状態変更案が発生した場合、その確定は FLOW-09 状態遷移フローで行う。

### 6.7 Summary Manifest への処理フラグ要約

Summary Manifest では、ノード見出しに状態のみを記載する。

```text
ID:（参照元 / ノード名）［状態］
```

処理フラグは、原則としてノード見出しには含めない。

必要に応じて、`構成（要素・関係）`、`ロジック`、`実態` のいずれかに、処理フラグの要約を記載する。

例:

```text
C1.2:（C1, B1.2.1, E1.4 / UI実装）［差戻し］
	構成（要素・関係）:
	E1.4 の反例により、B1.2.1 に対応する UI 実装の修正対象となっている。

	ロジック:
	修正要否あり。影響範囲探索要否あり。修正後に再検証要否あり。

	実態:
	未成立。FLOW-09 状態遷移後、FLOW-04 修正フローの対象となる。
```

この場合、詳細な修正理由、原因層候補、検証結果、次フロー候補は、C1.2 の Node File または E1.4 の Node File に記録する。

### 6.8 処理フラグの解消

処理フラグは、対応する FLOW の実行または人間の確認によって解消される。

処理フラグの解消例は以下とする。

```text
修正要否あり:
	FLOW-04 修正フローで修正案が作成され、FLOW-05 差分更新フローで反映された場合に解消候補となる。

影響範囲探索要否あり:
	FLOW-06 影響範囲探索フローで影響範囲が確認された場合に解消候補となる。

検証計画更新要否あり:
	FLOW-07 検証計画生成フローで検証計画が更新された場合に解消候補となる。

再検証要否あり:
	再検証が実行され、FLOW-08 検証証跡記録フローで新しい証跡が記録された場合に解消候補となる。

上位変更提案要否あり:
	FLOW-11 上位変更提案フローで提案が作成され、人間により確認または承認された場合に解消候補となる。

状態遷移要否あり:
	FLOW-09 状態遷移フローで状態変更案が確定または却下された場合に解消される。
```

処理フラグの解消は、必要に応じて状態変更案を伴う。

### 6.9 状態管理とファイル唯一正

状態、状態変更理由、処理フラグ、次フロー候補は、現在の VALIS ファイル群に記録された内容を正式な判断基準とする。

チャット履歴、作業メモ、一時応答、生成途中説明は、状態管理の唯一正として扱わない。

Summary Manifest は状態と処理フラグ要約を保持し、Node File は状態理由および処理フラグ詳細を保持する。

変更履歴は Git に委ねる。

---

## 7. 構造順序

VALIS の大枠の階層は以下とする。

- **A: 仕様**
- **B: 機能分解**
- **C: 実装**
- **D: 検証計画**
- **E: 検証証跡**  
    必要に応じて別管理してよい。


### 7.1 層の原則

- 大枠の階層は固定する
- 各階層内では再階層化を許可する
- 層間責務は越境しない
- 実行計画は VALIS 本体に含めない

### 7.2 実行計画の扱い

実行計画は、時点依存・環境依存・運用依存が強いため、**VALIS 本体では表現しない**。  
必要に応じて、別ファイルとして生成・管理する。

---

## 8. 各階層の意味

### A: 仕様

- システムの目的
- 成立条件
- 制約原則
- 判断基準
- 上位概念

仕様は、下位に対する判断基準として伝播する。

### B: 機能分解

- 仕様を満たすための機能単位
- 機能責務
- デザイン・画面・操作可能性
- 接合責務
- 制約の具体化

機能は、ユーザー価値および仕様成立を担保する単位である。

### C: 実装

- 機能を実行可能構造へ変換する
- 処理単位
- UI実装単位
- 接合実装
- 中核実装要素
- 可変末端
- 対応する実装ファイル

実装は、機能の意味を保存したまま実行可能構造へ変換する層である。

C層 Node File は、実装の意味、責務、中核要素、可変部、対応する実装ファイルへの参照を保持する。  
実際に実行される実装コード本体は、原則として `src/` 配下に配置する。  
`valis/nodes/C/` は実装コード置き場ではない。

### D: 検証計画

- 何を担保確認するか
- どの観点で確認するか
- どのノードを対象にするか
- どの制約を確認するか
- 回帰確認の対象

検証計画は、仕様・機能・実装の対応関係を確認可能にする。

### E: 検証証跡

- E 層証跡ID
- 対応する D 層検証計画ID
- 検証対象ノードID
- 実行対象
- 実行対象バージョン
- 実行ログ
- 結果
- 差分
- 承認記録
- 回帰結果
- 反例
- 証跡資料

検証証跡は、検証結果を再確認可能な形で保存する。

検証証跡は、対応する検証計画、検証対象、実行対象バージョン、有効条件、無効化条件、現在有効性を保持する。

---

## 9. 階層構造の原理

### 9.1 上位から下位への具体化

VALIS は、上位から下位へ以下のように意味を下ろす。

- 上位は自然言語に近い意図
- 中位は担保機能と制約
- 下位は実装責務
- 末端はコーディング表現

### 9.2 曖昧さの扱い

曖昧さは欠陥ではなく、上位から下位へ具体化される過程で吸収される。

必要なのは曖昧さの消去ではなく、以下を追跡可能にすることである。

- どこで意味が固定されたか
- どこで具体化されたか
- どこがまだ未確定か

### 9.3 属性伝播

ノード属性は上位から下位へ伝播する。  
とくに以下は伝播対象となる。

- セキュリティ制約
- 認証・認可要件
- 整合性要件
- 優先度
- 例外条件
- 禁止事項
- 監査可能性

---

## 10. 接合責務

### 10.1 原則

子同士の暗黙接続は原則として避ける。  
複数の子機能・子実装が接合を必要とする場合、**接合専用ノード**を設ける。

### 10.2 接合ノードの役割

接合ノードは、以下の責務を持つ。

- 統合
- 調停
- 共通前提の明示
- 優先順位の整理
- 複数ノードの結果統合

### 10.3 接合の意味

横方向の複雑さを、縦方向の責務分解へ変換する。  
これにより、構造の可読性と検証可能性を維持する。

---

## 11. 優先度

### 11.1 優先度の必要性

子ノードには優先度を与える。  
優先度は単なる補助属性ではなく、以下を示す。

- 何が本質か
- 何が補助か
- 何を先に読むか
- 競合時に何を優先するか

### 11.2 優先度の分離

優先度は少なくとも次に分けて扱う。

- **重要度**: 本質性
- **評価順序**: 先に確認すべき順
- **競合優先順位**: 衝突時の優先順

---

## 12. サマリとノード本体

### 12.1 サマリの役割

サマリは読むための構造である。  
サマリには以下を記載しない。

- 詳細仕様
- 実装内容
- 履歴
- 議論ログ
- 冗長な説明

### 12.2 ノード本体の役割

厳密な定義はノード本体に記述する。  
必要な場合のみ本体を参照する。

### 12.3 1ノード1ファイル

各ノードは、原則として1つのノード本体ファイルに対応する。

```text
A1        -> valis/nodes/A/A1.md
A1.1      -> valis/nodes/A/A1.1.md
B1        -> valis/nodes/B/B1.md
B1.1      -> valis/nodes/B/B1.1.md
C1.0      -> valis/nodes/C/C1.0.md
D1        -> valis/nodes/D/D1.md
E1        -> valis/nodes/E/E1.md
```

Node File の配置は、VALIS の意味定義を保存するための配置である。  
実装コード本体およびテストコード本体は Node File ではない。

```text
実装コード:
	src/ 配下に配置する。

テストコード:
	tests/ 配下に配置する。
```

サマリは構造と読解経路を示し、ノード本体は詳細定義を保持する。

### 12.4 ファイル唯一正

VALIS における唯一正は、VALIS Summary Manifest および各ノード本体ファイルである。

チャット履歴、作業メモ、一時的な応答、生成途中の説明は、唯一正として扱わない。

変更履歴は VALIS 本体には保持しない。  
変更履歴は Git などの外部バージョン管理に委ねる。

したがって、VALIS は以下の原則に従う。

- 判断基準は現在のファイル内容とする
- チャット履歴を正式な仕様根拠にしない
- 合意された内容は、必要に応じてファイルへ反映する
- ファイルへ反映されていない内容は、未反映の入力または提案として扱う
- 変更履歴・議論履歴・作業ログは VALIS ノード本体に残さない

検証証跡 E は、履歴管理ではなく、現在有効な検証結果・証拠・反例・確認結果を保持する層である。

E 層証跡は、対象バージョン、有効条件、無効化条件に基づいて現在有効性を判断する。

---
### 12.5 Summary Manifest と Node File の記録分担

Summary Manifest と Node File は、同じ内容を重複して保持しない。

Summary Manifest は、VALIS 全体を読むための構造、階層、参照、状態、処理フラグ要約、読み込み経路を保持する。

Node File は、各ノードの詳細な意味内容、状態変更理由、処理フラグ詳細、検証との関係、起点証跡、未確定事項、確認事項を保持する。

Summary Manifest は、詳細定義そのものを保持する場所ではない。  
Node File は、構造全体の一覧性を担う場所ではない。

記録分担の原則は以下とする。

```
Summary Manifest に保持するもの:
	構造
	階層
	参照関係
	ノード状態
	読み込み経路
	処理フラグ要約
	状態変更理由の要約
	次フロー候補の要約
	Manifest 初期登録要否の要約
	Manifest 反映要否の要約
	未確定事項の要約
	確認事項の要約
	E 層証跡IDの要約
	対応する D 層検証計画IDの要約
	検証対象ノードIDの要約
	実行対象バージョンの要約
	対応する実装ファイルパスの要約
	対応するテストファイルパスの要約
	証跡の現在有効性の要約

Node File に保持するもの:
	詳細定義
	構成の詳細
	ロジックの詳細
	実態の詳細
	状態変更案の詳細
	状態変更理由の詳細
	処理フラグ詳細
	処理フラグインスタンス
	処理フラグ解消候補
	残存処理フラグ
	次フロー候補の理由
	参照種別の詳細
	制約競合の詳細
	起点証跡
	検証計画との関係
	検証証跡との関係
	E 層証跡ID
	対応する D 層検証計画ID
	検証対象ノードID
	実行対象
	実行対象バージョン
	対応する実装ファイルパス
	対応するテストファイルパス
	証跡の有効条件
	証跡の無効化条件
	証跡の現在有効性
	未確定事項の詳細
	人間確認事項の詳細
```

Summary Manifest に詳細を過剰に記載しない。  
Node File に構造全体の要約を過剰に記載しない。

両者の内容が矛盾する場合は、現在の VALIS ファイル群を確認し、必要に応じて FLOW-05 差分更新フロー、FLOW-06 影響範囲探索フロー、または FLOW-09 状態遷移フローへ接続する。

### 12.12.2 Manifest 初期登録

Manifest 初期登録とは、新規 Node File を作成したとき、そのノードを Summary Manifest に初めて登録し、VALIS 構造上の読み込み対象として索引可能にする作業である。

Manifest 初期登録は、Manifest 反映とは区別する。

```text id="manifest_initial_registration_distinction"
Manifest 初期登録:
	新規 Node File の存在、ID、状態、参照元、Node File パス、短い要約を Summary Manifest に初めて登録する。

Manifest 反映:
	既存登録済みノード、参照、状態、処理フラグ、実装対応、検証対応、次FLOW候補の変更を Summary Manifest に反映する。
```

新規 Node File は、Summary Manifest に初期登録されるまでは、後続 FLOW が安定して発見できる VALIS 構造として扱わない。

Manifest 初期登録では、以下を最小項目とする。

```text id="manifest_initial_registration_minimum_fields"
Manifest 初期登録の最小項目:
	ノードID
	ノード名
	所属層
	状態
	括弧内参照元
	参照種別の要約
	Node File パス
	短い要約
	処理フラグ要約
	次FLOW候補
```

必要に応じて、以下も初期登録に含める。

```text id="manifest_initial_registration_optional_fields"
必要に応じて登録する項目:
	対応する実装ファイルパス
	対応するテストファイルパス
	対応する検証計画ID
	対応する検証証跡ID
	実行対象バージョンの要約
	未確定事項の要約
	人間確認事項の要約
```

A/B/C/D/E 構造展開を行う場合、Summary Manifest は以下の初期登録を保持する。

```text id="manifest_initial_registration_layer_rules"
A層 Node File:
	仕様ノードとして、ID、状態、要約、Node File パスを登録する。

B層 Node File:
	機能ノードとして、参照元A、状態、要約、Node File パスを登録する。

C層 Node File:
	実装ノードとして、参照元A/B、状態、要約、Node File パス、対応する src/ パスを登録する。

D層 Node File:
	検証計画ノードとして、検証対象A/B/C、状態、要約、Node File パス、対応する tests/ パスを登録する。

E層 Node File:
	検証証跡ノードとして、対応D、検証対象A/B/C、状態、要約、Node File パス、検証結果または実行対象バージョンの要約を登録する。
```

Summary Manifest は、Manifest 初期登録においても詳細本文を保持しない。

```text id="manifest_initial_registration_forbidden_content"
Manifest 初期登録で保持しないもの:
	Node File 全文
	実装コード全文
	テストコード全文
	検証ログ全文
	実行計画本文
	作業ログ本文
	内部推論過程
```

新規 Node File を作成したにもかかわらず Summary Manifest へ初期登録していない場合、当該作業は VALIS 構造上の完了条件を満たさない。

Manifest 初期登録後に、状態、参照、処理フラグ、実装対応、検証対応、次FLOW候補が変わった場合は、Manifest 反映として扱う。

### 12.5.1 Summary Manifest の保持範囲

Summary Manifest は、VALIS 全体の現在構造を読むための索引である。

Summary Manifest は、後続 FLOW が対象ノード、参照関係、状態、処理フラグ、実装対応、検証対応、次 FLOW 候補を判断できる範囲に限って情報を保持する。

Summary Manifest は、詳細本文、実装本文、検証ログ全文、作業履歴全文を保持しない。

```text id="manifest_retention_scope_keep"
Summary Manifest に保持するもの:
	ノードID
	ノード名
	所属層
	ノード状態
	ID階層
	親子関係の要約
	括弧内参照元の要約
	参照種別の要約
	制約競合の要約
	Node File パス
	対応する実装ファイルパスの要約
	対応するテストファイルパスの要約
	検証対象ノードIDの要約
	対応する D 層検証計画IDの要約
	対応する E 層証跡IDの要約
	実行対象バージョンの要約
	証跡の現在有効性の要約
	ノード内容の短い要約
	処理フラグ要約
	状態変更案の要約
	状態変更理由の要約
	残存処理フラグ要約
	次FLOW候補の要約
	Manifest反映要否の要約
	未確定事項の要約
	人間確認事項の要約
	読み込み経路
```

Summary Manifest における要約は、詳細の代替ではない。

詳細確認が必要な場合、実行主体は Summary Manifest の要約から対象 Node File、実装ファイル、テストファイル、検証計画、検証証跡へ移動して読む。

### 12.5.2 Summary Manifest に保持しないもの

Summary Manifest には、以下を保持してはならない。

```text id="manifest_retention_scope_exclude"
Summary Manifest に保持しないもの:
	Node File 全文
	実装コード全文
	テストコード全文
	詳細な検証ログ全文
	詳細な実行ログ全文
	実行計画本文
	作業ログ本文
	チャット履歴全文
	内部推論過程
	長い議論履歴
	Git 差分全文
	過去バージョンの本文
	処理フラグインスタンス全文
	状態変更理由の詳細本文
	制約競合の詳細本文
	証跡の生ログ
	外部コマンド出力全文
```

これらは、それぞれ以下を正とする。

```text id="manifest_retention_scope_authority"
Node File 全文:
	valis/nodes/ 配下の対象 Node File を正とする。

実装コード全文:
	src/ 配下の実装ファイルを正とする。

テストコード全文:
	tests/ 配下のテストファイルを正とする。

検証計画詳細:
	D 層 Node File を正とする。

検証証跡詳細:
	E 層 Node File を正とする。

作業計画本文:
	operations/plans/ 配下のファイルを正とする。

作業ログ本文:
	operations/logs/ 配下のファイルを正とする。

変更履歴:
	Git などの外部バージョン管理を正とする。
```

### 12.5.3 保持粒度

Summary Manifest の保持粒度は、後続 FLOW が次の判断をできる最小限とする。

```text id="manifest_retention_granularity"
保持粒度の基準:
	対象ノードを特定できる
	読むべき Node File を特定できる
	関連する実装ファイルまたはテストファイルを特定できる
	検証計画または検証証跡との対応を特定できる
	現在状態を判断できる
	処理フラグ要約を判断できる
	残存処理と次FLOW候補を判断できる
	人間確認が必要か判断できる
```

上記を超える詳細は、Summary Manifest に展開せず、対応する Node File、実装ファイル、テストファイル、検証計画、検証証跡、作業計画、作業ログに分離する。

### 12.5.4 Manifest 反映時の保持範囲判定

Manifest 反映を行う場合、実行主体は反映内容を以下に分類する。

```text id="manifest_reflection_retention_targets"
反映先分類:
	Summary Manifest に要約として反映するもの
	Node File に詳細として反映するもの
	src/ に実装コードとして反映するもの
	tests/ にテストコードとして反映するもの
	operations/plans/ に作業計画として分離するもの
	operations/logs/ に作業ログとして分離するもの
	Git など外部履歴へ委ねるもの
```

反映先を分類できない場合、Summary Manifest へ推測で詳細を混入してはならない。

その場合は、Manifest 反映確認待ち、Node File 詳細化、または次 FLOW 候補として扱う。

### 12.5.5 Operation核駆動における保持範囲調整

Operation Definition が VALIS の先行制御構文となる場合でも、Summary Manifest は Operation Definition の複製ではない。  
Summary Manifest は、Operation によって駆動された結果として生じた構造・状態・参照・未解決前提の要約を保持する。

Summary Manifest は、以下の4種を分離して扱う。

```text id="manifest_retention_adjustment_four_groups"
保持分類:
	1. 正本参照:
		対象の正本ファイル、Node File、src、tests、operations、外部履歴を指し示す情報。

	2. 構造要約:
		ノード、層、参照、状態、対応ファイル、検証対応、処理フラグの要約。

	3. 前提要約:
		前提フィードバックの結果のうち、後続 FLOW、承認、検証、Manifest 初期登録、Manifest 反映、NEXT に影響するもの。

	4. 接続要約:
		次に読むべき対象、次FLOW候補、確認待ち、再開条件を判断するための要約。
```

Summary Manifest は、以下の情報を全文保持しない。

```text id="manifest_retention_adjustment_forbidden"
全文保持しないもの:
	Operation Definition 本文
	VALIS Identity Kernel 本文
	前提フィードバック機構本文
	Flow Definition 本文
	起動テンプレート本文
	Node File 本文
	実装コード本文
	テストコード本文
	検証ログ本文
	作業ログ本文
	毎回の READ / TASK / INPUT / NEXT 出力
	内部推論過程
	Git差分全文
```

Summary Manifest は、前提フィードバックの詳細ログではなく、構造判断に必要な結果要約のみを保持する。

```text id="manifest_premise_feedback_retention_scope"
保持できる前提フィードバック要約:
	不足している中核ファイルまたは未読中核ファイルの要約
	Manifest 初期登録未了の要約
	Manifest 反映未了の要約
	C層なしで src/ へ進めない状態の要約
	D層なしで tests/ へ進めない状態の要約
	E層証跡なしで検証済み報告できない状態の要約
	承認待ち、確認待ち、外部環境確認待ちの要約
	次FLOW候補または NEXT に影響する再開条件
```

Summary Manifest は、作業結果照合および出力前ゲートを支えるため、報告内容に対応する実体要約を保持できる。  
ただし、照合の詳細過程、コマンド出力全文、差分全文、内部判断過程は保持しない。

保持範囲を超える内容が発生した場合、Summary Manifest にはその詳細ではなく、詳細保存先への参照と必要最小限の要約だけを残す。


### 12.6 ノード本体ファイル記述規則

ノード本体ファイルは、Summary Manifest 上の各ノードに対応する詳細記録である。

ノード本体ファイルは、対象ノードの意味内容を、後続 FLOW が読み取れる粒度で記録する。

ノード本体ファイルには、必要に応じて以下を記載する。

```
ノードID:
	対象ノードの ID を記載する。

ノード名:
	対象ノードの名称を記載する。

層:
	A / B / C / D / E のいずれに属するかを記載する。

現在の状態:
	草案、提案中、レビュー中、承認済み、差戻し、凍結、廃止のいずれかを記載する。

親ノード:
	階層上の親ノードを記載する。

子ノード:
	階層上の子ノードを記載する。

参照元ノード:
	対象ノードの意味的依存、制約、由来となるノードを記載する。

参照先ノード:
	対象ノードを参照する、または対象ノードから意味接続されるノードを記載する。

参照種別:
	主所属、意味依存、制約由来、実装対象、検証対象、証跡起点、接合対象、影響対象などを記載する。

接合ノード:
	複数ノードの統合、調停、共通前提、優先順位整理に関係するノードを記載する。

制約競合:
	複数の制約、参照、状態、ユーザー指示が同時に成立しない可能性がある場合に記載する。

関連する検証計画:
	対象ノードに対応する D 層検証計画を記載する。

関連する検証証跡:
	対象ノードに対応する E 層検証証跡を記載する。

E層証跡ID:
	E 層検証証跡ノードを識別する ID を記載する。

対応するD層検証計画ID:
	当該証跡が基づく D 層検証計画ノードを記載する。

検証対象ノードID:
	当該証跡が検証対象とする A/B/C ノードを記載する。

実行対象:
	検証を実行したコード、成果物、設定、画面、API、外部対象などを記載する。

実行対象バージョン:
	検証を実行した対象を再識別するためのコミットID、ビルドID、成果物バージョン、設定バージョンなどを記載する。

対応する実装ファイル:
	C層 Node File が意味上対応する src/ 配下の実装ファイルパスを記載する。

対応するテストファイル:
	D層または E層 Node File が意味上対応する tests/ 配下のテストファイルパスを記載する。

証跡の有効条件:
	当該証跡を現在有効な証跡として扱える条件を記載する。

証跡の無効化条件:
	当該証跡を現在有効な証跡として扱えなくなる条件を記載する。

現在有効性:
	有効、無効化候補、無効、確認必要のいずれかを記載する。

構成（要素・関係）:
	ノードを構成する要素、および要素間の関係を記述する。

ロジック:
	構成がどのように解釈・展開・作用するかを記述する。

実態:
	ロジックの作用によって成立する状態・構造を記述する。

状態変更案:
	対象ノード、現在の状態、変更後の状態候補、承認要否を記述する。

状態変更理由:
	状態変更案の起点、理由、関連ノード、関連証跡、関連処理フラグを記述する。

処理フラグ詳細:
	修正要否、影響範囲探索要否、検証計画更新要否、再検証要否、上位変更提案要否、状態遷移要否、次フロー候補を記述する。

処理フラグインスタンス:
	処理フラグID、対象ノード、種別、値、起点、発生理由、解消条件、残存理由、次フロー候補を記述する。

処理フラグ解消候補:
	解消対象、解消理由、解消根拠、解消後に残る処理フラグ、再発生しうる条件、人間確認の要否を記述する。

残存処理フラグ:
	当該処理後も未解消として残る処理フラグと、その理由を記述する。

次フロー候補:
	後続処理として実行候補となる FLOW と、その理由を記述する。

起点証跡:
	状態変更案または処理フラグの根拠となる E 層検証証跡を記述する。

未確定事項:
	判断不能な点、追加確認が必要な点、保留事項を記述する。

人間確認事項:
	人間の確認または承認が必要な点を記述する。
```

すべての項目を常に記載する必要はない。

ただし、状態変更案、状態変更理由、処理フラグ、処理フラグインスタンス、処理フラグ解消候補、残存処理フラグ、次フロー候補、参照種別、制約競合、起点証跡、E 層証跡ID、実行対象バージョン、証跡の現在有効性が発生した場合は、後続 FLOW が読める形で記録する。

ノード本体ファイルは、作業ログ、議論ログ、チャット履歴、生成途中の説明を保持しない。  
これらは VALIS の唯一正として扱わない。

ノード本体ファイルに記録する内容は、現在有効な意味定義、状態理由、処理フラグ詳細、検証関係、確認事項に限定する。

### 12.7 Summary Manifest に保持する要約項目

Summary Manifest には、Node File の詳細をそのまま転記しない。

Summary Manifest に保持するのは、読解、探索、状態確認、次フロー判断に必要な要約である。

Summary Manifest には、必要に応じて以下を記載する。

```
ノードID:
	対象ノードの ID。

ノード名:
	対象ノードの名称。

状態:
	対象ノードの現在状態。

参照元:
	対象ノードの意味的依存、制約、由来。

参照種別の要約:
	読解、影響範囲探索、検証対象、処理フラグ判断に必要な参照種別。

制約競合の要約:
	後続 FLOW が確認すべき制約競合の有無と概要。

E層証跡IDの要約:
	E 層証跡ノードを識別する ID。

対応するD層検証計画IDの要約:
	当該証跡が基づく D 層検証計画ノード。

検証対象ノードIDの要約:
	当該証跡が検証対象とする A/B/C ノード。

実行対象バージョンの要約:
	当該証跡が成立した実行対象バージョン。

対応する実装ファイルパスの要約:
	C層 Node File が意味上対応する src/ 配下の実装ファイルパス。

対応するテストファイルパスの要約:
	D層または E層 Node File が意味上対応する tests/ 配下のテストファイルパス。

証跡の現在有効性の要約:
	有効、無効化候補、無効、確認必要のいずれか。

構成（要素・関係）の要約:
	対象ノードが何と関係するかの要約。

ロジックの要約:
	対象ノードがどのように解釈・作用するかの要約。

実態の要約:
	対象ノードが現在どのような成立状態にあるかの要約。

処理フラグ要約:
	次に必要な処理の要約。

処理フラグインスタンスの有無:
	Node File に詳細な処理フラグインスタンスが存在するか。

状態変更理由の要約:
	状態変更案が発生している理由の要約。

次フロー候補の要約:
	後続処理として候補となる FLOW の要約。

未確定事項の要約:
	判断不能または保留されている事項の要約。

確認事項の要約:
	人間確認または承認が必要な事項の要約。
```

Summary Manifest のノード見出しには、状態のみを記載する。

処理フラグ、状態変更案、状態変更理由、次フロー候補を状態名として扱わない。

処理フラグや状態変更理由を Summary Manifest に記載する場合は、`構成（要素・関係）`、`ロジック`、`実態` のいずれかに要約として記載する。

詳細は Node File に記録する。

### 12.8 処理フラグ詳細の記録位置

処理フラグは、状態ではない。  
処理フラグは、当該ノードまたは関連ノードに対して次に必要な処理を示す。

処理フラグの詳細は、原則として対象 Node File に記録する。

処理フラグは、発生原因単位の処理フラグインスタンスとして記録する。

処理フラグが E 層検証証跡を起点として発生した場合は、対象 Node File に加えて、起点となる E 層 Node File にも処理フラグの根拠を記録できる。

処理フラグ詳細または処理フラグインスタンスには、必要に応じて以下を含める。

```
処理フラグID:
	処理フラグインスタンスを識別するID。

処理フラグ種別:
	修正要否
	影響範囲探索要否
	検証計画更新要否
	再検証要否
	上位変更提案要否
	状態遷移要否
	次フロー候補

処理フラグ値:
	あり
	なし
	確認必要

対象ノード:
	処理フラグが作用するノード。

発生理由:
	処理フラグが必要になった理由。

起点種別:
	ユーザー入力、変更、検証結果、反例、失敗、矛盾、未確定事項、制約競合、人間指示、E層証跡。

起点ノード:
	処理フラグ発生の起点となったノード。

起点証跡:
	E 層証跡が根拠となる場合の証跡。

発生FLOW:
	処理フラグを作成した FLOW。

関連参照種別:
	処理フラグの根拠または影響範囲に関係する参照種別。

関連制約:
	処理フラグの根拠または影響範囲に関係する制約。

解消条件:
	どの条件を満たせば処理フラグを解消候補にできるか。

処理フラグ解消候補:
	解消可能性、解消理由、解消根拠、解消後に残る処理フラグ。

残存処理フラグ:
	当該処理後も残る処理フラグ。

次フロー候補:
	処理フラグに対応して実行候補となる FLOW。

人間確認要否:
	人間の確認または承認が必要か。
```

Summary Manifest には、処理フラグ詳細ではなく、必要最小限の処理フラグ要約のみを記載する。

処理フラグインスタンスが1件以上残る場合は、Summary Manifest の処理フラグ要約を残す。

処理フラグインスタンスがすべて解消された場合にのみ、Summary Manifest の処理フラグ要約を削除候補または解消候補にできる。

処理フラグの確定、解消、却下、次フロー決定が必要な場合は、FLOW-09 状態遷移フローへ接続する。

### 12.9 状態変更理由の記録位置

状態変更理由は、状態変更案の根拠を示す。

状態変更理由の詳細は、原則として対象 Node File に記録する。

状態変更理由が E 層検証証跡を起点として発生した場合は、対象 Node File に加えて、起点となる E 層 Node File にも状態変更理由の根拠を記録できる。

状態変更理由には、必要に応じて以下を含める。

```
対象ノード:
	状態変更案の対象となるノード。

現在の状態:
	状態変更前の状態。

変更後の状態候補:
	状態変更後の候補状態。

状態変更の起点:
	入力、変更、検証結果、反例、失敗、矛盾、未確定事項、または証跡。

起点ノード:
	状態変更理由の発生元となるノード。

起点証跡:
	E 層証跡が根拠となる場合の証跡。

状態変更理由:
	なぜ状態変更案が必要になったか。

関連する処理フラグ:
	状態変更案に関係する処理フラグ。

次フロー候補:
	状態変更案に関連して実行候補となる FLOW。

承認要否:
	人間の確認または承認が必要か。
```

Summary Manifest には、状態変更理由の詳細ではなく、必要最小限の要約のみを記載する。

状態変更案が存在する場合でも、FLOW-09 状態遷移フローで確定されるまでは、対象ノードの状態を自動変更しない。

状態変更理由が不明確な場合は、状態を変更せず、未確定事項または人間確認事項として扱う。

### 12.10 実行計画・作業情報の扱い

実行計画、作業手順、担当、期限、スケジュール、リリース手順、デプロイ手順、運用手順、ロールバック手順は、VALIS 本体の恒常的な意味定義として扱わない。

これらは、時点依存、環境依存、運用依存が強い情報である。  
そのため、Summary Manifest または Node File に詳細を混入させない。

実行計画・作業情報に該当するものは、以下である。

```
実行計画・作業情報:
	実装作業手順
	開発タスク一覧
	作業順序
	担当者割当
	期限
	マイルストーン
	リリース手順
	デプロイ手順
	運用手順
	検証実行手順
	テスト実行順序
	作業チェックリスト
	移行計画
	ロールバック計画
	外部ツール上のタスク管理情報
	実行時点に依存するメモ
	一時的な作業計画
```

Summary Manifest には、実行計画・作業情報の詳細を記載しない。

Summary Manifest には、必要に応じて以下のみを要約として記載する。

```
Summary Manifest に記載できる要約:
	実行計画が別管理されていること
	実行計画の対象ノード
	実行計画の目的
	実行計画ファイルまたは外部管理先への参照
	実行計画に関連する処理フラグ要約
	実行計画に関連する状態変更理由の要約
	実行計画に関連する次フロー候補
	人間確認または承認要否
```

Node File には、実行計画・作業情報そのものを恒常的な意味定義として記録しない。

Node File には、必要に応じて以下のみを記録する。

```
Node File に記録できる内容:
	実行計画との関係
	実行計画を分離した理由
	実行計画の対象範囲
	実行計画に関係する前提
	実行計画に関係する制約
	実行計画により発生した状態変更案
	実行計画により発生した状態変更理由
	実行計画により発生した処理フラグ詳細
	実行計画により発生した処理フラグ解消候補
	実行計画により残存する処理フラグ
	実行計画に関連する次フロー候補
	実行計画ファイルまたは外部管理先への参照
	人間確認または承認事項
```

実行計画・作業情報が必要な場合は、VALIS 本体とは別に管理する。

実行計画・作業情報を別管理する場合でも、VALIS 本体との接続は失わない。  
対象ノード、関連 Node File、関連する検証計画、関連する検証証跡、処理フラグ、次フロー候補を明示する。

実行計画・作業情報が VALIS の意味構造に影響する場合は、実行計画側で直接変更せず、該当する FLOW へ接続する。

接続先の目安は以下とする。

```
VALIS 本体の修正が必要:
	FLOW-04 修正フロー

ファイル反映が必要:
	FLOW-05 差分更新フロー

影響範囲が未確定:
	FLOW-06 影響範囲探索フロー

検証計画の追加または更新が必要:
	FLOW-07 検証計画生成フロー

実行結果または検証結果を証跡化する必要:
	FLOW-08 検証証跡記録フロー

状態変更案、処理フラグ、処理フラグ解消候補、次フロー候補の確定が必要:
	FLOW-09 状態遷移フロー

再生成が必要:
	FLOW-10 再生成フロー

上位構造への変更提案が必要:
	FLOW-11 上位変更提案フロー

実行計画の分離判断が必要:
	FLOW-12 実行計画分離フロー
```

実行計画・作業情報は、VALIS の唯一正ではない。  
VALIS の唯一正は、VALIS Summary Manifest および各 Node File である。

実行計画・作業情報は、作業実行のための補助情報であり、仕様、機能、実装中核、検証観点、検証証跡の代替ではない。


### 12.11 実装コードとテストコードの配置

VALIS では、実装の意味定義と実行されるコード本体を分離する。

```text
C層 Node File:
	実装の意味、責務、中核要素、可変部、制約、判断根拠、対応する実装ファイルへの参照を保持する。

src/:
	実際に実行される実装コードを配置する。

tests/:
	実装コードに対するテストコード、検証用コード、回帰確認用コードを配置する。
```

`valis/nodes/C/` は実装コード置き場ではない。  
`valis/nodes/D/` および `valis/nodes/E/` もテストコード置き場ではない。

C層 Node File は、必要に応じて対応する `src/` 配下の実装ファイルパスを保持する。  
D層検証計画または E層検証証跡は、必要に応じて対応する `tests/` 配下のテストファイルパスを保持する。

Summary Manifest には、実装コード全文またはテストコード全文を記載しない。  
Summary Manifest には、読解、探索、再生成、検証接続に必要な範囲で、対応する実装ファイルパスおよびテストファイルパスの要約のみを記載する。

実装コードまたはテストコードが新規作成・更新された場合でも、それだけでは VALIS 構造が更新されたとは扱わない。  
対応する Node File および Summary Manifest への反映要否を確認する。



### 12.12 Manifest 反映

Manifest 反映とは、Summary Manifest に初期登録済みのノード、参照、状態、処理フラグ、実装対応、検証対応、次FLOW候補などに変更が発生した場合、その変更を Summary Manifest に必要最小限の構造要約として反映する作業である。

Summary Manifest は、作業ログではない。  
Manifest 反映では、後続 FLOW が読み込み対象、状態、参照、処理フラグ、次フロー候補、実装対応、検証対応を判断できる範囲に限って要約を保持する。

Manifest 反映は、Manifest 初期登録とは区別する。

```text
Manifest 初期登録:
	新規 Node File を Summary Manifest に初めて登録し、VALIS 構造上の読み込み対象として索引可能にする作業。

Manifest 反映:
	初期登録済みのノードまたは対応関係に発生した変更を、Summary Manifest の構造要約へ反映する作業。
```

Manifest 反映では、以下を記録対象にできる。

```text
Manifest 反映対象:
	ノードID
	ノード名
	状態
	親子関係
	参照元
	参照種別の要約
	制約競合の要約
	構成・ロジック・実態の要約
	対応する Node File パス
	対応する実装ファイルパス
	対応するテストファイルパス
	A/B/C/D/E 構造展開の要約
	検証計画IDの要約
	検証証跡IDの要約
	実行対象バージョンの要約
	証跡の現在有効性の要約
	処理フラグ要約
	状態変更理由の要約
	残存処理フラグの要約
	次FLOW候補の要約
	未確定事項の要約
	確認事項の要約
```

Manifest 反映では、以下を Summary Manifest に記載しない。

```text
Manifest 反映で記載しないもの:
	Node File 全文
	実装コード全文
	テストコード全文
	検証ログ全文
	実行計画本文
	作業ログ本文
	内部推論過程
	詳細な実装手順
	詳細なテスト手順
```

Manifest 反映が必要になる主な条件は以下とする。

```text
Manifest 反映が必要な変更:
	初期登録済み Node File の要約、状態、参照、処理フラグ、次FLOW候補が変わった
	C層 Node File と src/ 配下の実装ファイルの対応が変わった
	D層 Node File と tests/ 配下のテストファイルの対応が変わった
	D層検証計画または E層検証証跡の要約、対象、実行対象バージョン、有効性が変わった
	A/B/C/D/E 構造展開ゲートの達成状況、未達項目、後続FLOW候補が変わった
	状態変更案、状態変更理由、処理フラグ、処理フラグ解消候補、残存処理フラグが変わった
	作業結果照合により Summary Manifest 上の要約と実際の成果物の不一致が見つかった
```

新規 Node File を作成した場合は、まず Manifest 初期登録として扱う。  
初期登録後に状態、参照、処理フラグ、実装対応、検証対応、次FLOW候補がさらに変わった場合は Manifest 反映として扱う。

Manifest 反映が不要になる主な条件は以下とする。

```text
Manifest 反映が不要な変更:
	Node File の詳細本文のみの変更で、Summary Manifest の構造要約に影響しない
	src/ 配下の実装可変部のみの変更で、C層 Node File の対応や Summary Manifest の要約に影響しない
	tests/ 配下のテスト内部実装のみの変更で、D/E層の要約や証跡要約に影響しない
	operations/ 配下の実行計画または作業ログのみを変更した
	一時ファイルのみを扱った
```

Manifest 反映が必要か判断できない場合は、反映不要として処理してはならない。  
その場合は確認待ち、次FLOW候補、または該当 Node File の詳細確認として扱う。

Manifest 反映後、Summary Manifest と Node File の内容が完全一致する必要はない。  
Summary Manifest は構造要約のみを保持し、詳細は対応する Node File、`src/`、`tests/`、`operations/`、Git 履歴、または外部証跡を正とする。

作業結果照合で「Manifest 反映済み」と報告する場合、Summary Manifest には対象変更に対応する必要最小限の構造要約が存在していなければならない。

### 12.12.1 A/B/C/D/E 構造展開と Summary Manifest

Summary Manifest は、A/B/C/D/E の構造展開結果を後続 FLOW が読める形で保持する。

新規作成系の作業、または実装コード・テストコード・検証証跡を伴う作業では、Summary Manifest は以下の構造が存在するかを索引できなければならない。

```text
構造展開の索引対象:
	A層 仕様 Node File
	B層 機能 Node File
	C層 実装 Node File
	D層 検証計画 Node File
	対応する src/ 実装ファイルパス
	対応する tests/ テストファイルパス
	E層 検証証跡 Node File
```

A/B/C/D/E は、ID階層上の親子関係として入れ子にしない。  
A/B/C/D/E の具体化関係、実装対象、検証対象、証跡起点は、括弧内参照元および参照種別の要約によって表す。

```text
Summary Manifest 上の構造展開例:
	A1:（/ GAS ハローワールドWebアプリ仕様）［草案］
		Node File: valis/nodes/A/A1.md

	B1:（A1 / ブラウザ表示機能）［草案］
		Node File: valis/nodes/B/B1.md

	C1:（B1 / GAS Webアプリ実装）［草案］
		Node File: valis/nodes/C/C1.md
		実装ファイル: src/Code.gs

	D1:（C1, B1 / ブラウザ表示検証計画）［草案］
		Node File: valis/nodes/D/D1.md
		テストファイル: tests/hello-world.test.cjs

	E1:（D1, C1 / ローカル検証証跡）［草案］
		Node File: valis/nodes/E/E1.md
```

Summary Manifest は、上記の詳細本文を保持しない。  
Summary Manifest は、ノードID、ノード名、状態、参照元、Node File パス、実装ファイルパス、テストファイルパス、検証計画ID、検証証跡ID、処理フラグ要約、次FLOW候補のみを必要最小限で保持する。

新規 Node File を作成したにもかかわらず Summary Manifest に登録されていない場合、そのノードは後続 FLOW から読み込み対象として安定的に発見できない。  
そのため、構造展開ゲートが適用された作業では、Summary Manifest への初期登録または Manifest 反映を作業完了条件に含める。

### 12.13 作業完了条件と Summary Manifest の関係

Summary Manifest は作業完了チェックリストそのものではない。
ただし、作業完了条件のうち、VALIS 構造として後続 FLOW が参照する必要がある要約は Summary Manifest に反映される。

Summary Manifest に反映すべき作業完了関連情報は、以下に限定する。

```text
Summary Manifest に反映する作業完了関連情報:
	作成または更新されたノードの要約
	ノード状態または状態変更案の要約
	参照元、参照種別、制約競合の要約
	対応する Node File パス
	対応する実装ファイルパス
	対応するテストファイルパス
	検証計画または検証証跡との接続要約
	処理フラグ要約
	残存処理フラグ要約
	次FLOW候補
	未確定事項または確認事項の要約
```

Summary Manifest に反映しない作業完了関連情報は、以下とする。

```text
Summary Manifest に反映しないもの:
	作業完了チェックリスト全文
	実行中の内部確認ログ
	詳細な作業手順
	詳細な差分ログ
	内部推論過程
	TASK / INPUT / NEXT の表示全文
```

作業完了条件が未達の場合、その未達項目を Summary Manifest に全文記録する必要はない。
ただし、未達項目が後続 FLOW の判断に必要な場合は、処理フラグ要約、残存処理フラグ、次FLOW候補、または確認事項として必要最小限に要約する。

作業完了条件を満たした場合でも、Summary Manifest に反映すべき構造変更が存在しない場合は、Summary Manifest を更新しないでよい。
その場合でも、対象 Node File、実装ファイル、テストファイル、検証証跡との矛盾がないことを確認する。


### 12.13.1 強化された作業完了条件の保持範囲

Summary Manifest は、作業完了チェックリスト全文を保持しない。
ただし、作業完了条件を満たしたと報告するために必要な構造要約は、Summary Manifest 上に存在していなければならない。

```text id="manifest_completion_support_fields"
作業完了報告を支えるために必要な要約:
	作成または更新された Node ID
	ノード名
	ノード状態または状態変更案の要約
	参照元および参照種別
	Node File パス
	対応する実装ファイルパス
	対応するテストファイルパス
	検証計画ID
	検証証跡ID
	Manifest 初期登録済みかどうか
	Manifest 反映が必要な変更の要約
	残存処理フラグ要約
	次 FLOW 候補
```

以下の場合、Summary Manifest 上の構造要約が不足しているため、作業完了として扱わない。

```text id="manifest_completion_not_supported"
Summary Manifest 上で完了を支えられない場合:
	新規 Node File があるが、Summary Manifest に Node ID と Node File パスがない
	実装ファイルがあるが、対応する C層 Node File と実装ファイルパスの要約がない
	テストファイルがあるが、対応する D層または E層との接続要約がない
	検証済みと報告しているが、対応する E層証跡要約がない
	Manifest 反映済みと報告しているが、対象変更の構造要約がない
	残存処理があるのに、次 FLOW 候補または処理フラグ要約が必要範囲で記録されていない
```

Summary Manifest は、作業完了条件の判定ログ、詳細な差分ログ、内部確認ログ、作業結果照合チェックリスト全文を保持しない。
これらは必要に応じて `TASK` / `INPUT` / `NEXT`、Node File、`operations/plans/`、`operations/logs/`、または Git 差分で扱う。

### 12.14 作業結果照合と Summary Manifest

Summary Manifest は、作業結果照合のために必要な構造要約を保持する。  
ただし、Summary Manifest は作業結果照合ログ、詳細差分ログ、内部確認ログを保持する場所ではない。

作業結果照合において、Summary Manifest は以下の一致確認に使われる。

```text id="manifest_work_result_collation_scope"
Summary Manifest で確認するもの:
	作成または更新された Node File の登録有無
	A/B/C/D/E の構造展開結果
	Node ID、状態、参照元、参照種別の要約
	Node File パス
	対応する実装ファイルパス
	対応するテストファイルパス
	D層検証計画ID
	E層検証証跡ID
	処理フラグ要約
	残存処理フラグ要約
	次FLOW候補
```

作業結果照合で Summary Manifest に保持しないものは以下とする。

```text id="manifest_work_result_collation_exclusions"
保持しないもの:
	作業結果照合チェックリスト全文
	Git diff 全文
	作成・更新ファイルの全文
	実装コード全文
	テストコード全文
	検証ログ全文
	内部推論過程
	TASK / INPUT / NEXT の表示全文
```

作業結果照合で「Manifest 初期登録済み」または「Manifest 反映済み」と報告する場合、Summary Manifest には対象ノードまたは対応関係の必要最小限の構造要約が存在していなければならない。

```text id="manifest_work_result_collation_required_entries"
必要な登録・反映:
	A層 Node File を作成した場合、A層ノード要約と Node File パス
	B層 Node File を作成した場合、B層ノード要約、参照元A、Node File パス
	C層 Node File を作成した場合、C層ノード要約、参照元A/B、Node File パス、必要に応じた src/ パス
	D層 Node File を作成した場合、D層検証計画要約、検証対象、Node File パス、必要に応じた tests/ パス
	E層 Node File を作成した場合、E層証跡要約、対応D、検証対象、Node File パス、実行対象バージョン要約
```

Summary Manifest に対象要約が存在しない場合、実行主体はその対象を「Manifest 初期登録済み」「Manifest 反映済み」「整合性確認済み」と報告してはならない。

作業結果照合で不一致が見つかった場合、Summary Manifest には不一致の詳細ログを保存しない。  
ただし、後続 FLOW の判断に必要な場合は、処理フラグ要約、残存処理フラグ、次FLOW候補、または確認事項として必要最小限に要約してよい。

### 12.15 承認ゲートと Summary Manifest

Summary Manifest は、承認ゲートの判定に必要な構造要約を保持する。  
ただし、Summary Manifest は承認ログ全文、会話全文、内部判断ログを保持する場所ではない。

承認ゲートに関して Summary Manifest に保持してよいものは以下とする。

```text id="manifest_approval_gate_summary_fields"
保持してよいもの:
	対象ノードID
	対象ノードの現在状態
	対象ノードが草案、提案中、レビュー中、承認済み、差戻し、凍結、廃止のいずれか
	明示承認が必要かどうかの要約
	承認が必要な理由の短い要約
	承認なしで進めてよい作業範囲の要約
	承認後に接続する次FLOW候補
	承認なしで残る処理フラグ要約
```

Summary Manifest に保持してはならないものは以下とする。

```text id="manifest_approval_gate_non_fields"
保持しないもの:
	承認確認の会話全文
	内部判断ログ
	詳細な承認チェックリスト全文
	外部デプロイ手順全文
	認証情報、秘密情報、権限情報の詳細
	実装コード全文
	テストコード全文
```

草案 Node File の作成、非破壊的な `src/` 実装、非破壊的な `tests/` 作成、ローカル検証、Manifest 初期登録は、Summary Manifest 上で `承認済み` 状態として扱わない。

```text id="manifest_approval_gate_state_rule"
状態扱い:
	草案作成は承認済み化ではない。
	Manifest 初期登録は承認済み化ではない。
	ローカル検証証跡の記録は外部環境承認ではない。
	承認済み状態への遷移は FLOW-09 状態遷移フローで扱う。
```

承認ゲートによって停止または確認待ちになった場合、Summary Manifest には、必要に応じて処理フラグ要約または次FLOW候補のみを保持する。

```text id="manifest_approval_gate_flag_examples"
処理フラグ要約例:
	承認要否: あり
	承認対象: 外部デプロイ
	次FLOW候補: FLOW-09 状態遷移フロー / FLOW-08 検証証跡記録フロー
	残存理由: 実環境確認が未実施
```

### 12.16 FLOW実行契約と Summary Manifest

Summary Manifest は、FLOW実行契約そのものの本文を保持する場所ではない。  
FLOW実行契約の定義本文は VALIS Flow Definition を正とする。

ただし、Summary Manifest は、FLOW実行契約を実行可能にするための構造要約を保持する。

```text id="manifest_flow_execution_contract_support_fields"
Summary Manifest が支える FLOW実行契約項目:
	対象ノードID
	対象ノード名
	対象層
	現在状態
	参照元
	Node File パス
	実装ファイルパス
	テストファイルパス
	検証計画ノード
	検証証跡ノード
	処理フラグ要約
	次FLOW候補
	承認ゲート要約
	構造展開ゲートの達成状況要約
	Manifest 初期登録済みかどうか
	Manifest 反映が必要かどうか
```

Summary Manifest に保持してはならないものは以下とする。

```text id="manifest_flow_execution_contract_non_fields"
Summary Manifest に保持しないもの:
	FLOW実行契約本文の全文
	各FLOWの詳細チェックリスト全文
	作業結果照合ログ全文
	内部判断ログ
	実装コード全文
	テストコード全文
	検証ログ全文
	承認会話全文
```

FLOW実行契約で「Manifest 初期登録済み」「Manifest 反映済み」「構造展開ゲート達成済み」「検証接続済み」と報告する場合、Summary Manifest にはそれを支える必要最小限の構造要約が存在していなければならない。

```text id="manifest_flow_execution_contract_report_rule"
報告条件:
	C層実装 Node File 作成済みと報告する場合、C層ノード要約と Node File パスがある。
	src/ 実装作成済みと報告する場合、対応する C層ノード要約と src/ パスがある。
	D層検証計画作成済みと報告する場合、D層ノード要約と検証対象がある。
	tests/ 作成済みと報告する場合、対応する D/E層ノード要約または検証接続要約がある。
	E層検証証跡作成済みと報告する場合、E層ノード要約、対応D、検証対象、実行対象バージョン要約がある。
```

Summary Manifest に必要な構造要約がない場合、実行主体は FLOW実行契約を満たしたものとして報告してはならない。  
不足がある場合は、Manifest 初期登録、Manifest 反映、作業結果照合、または次FLOW候補として扱う。

### 12.17 VALIS実行サイクル再接続と Summary Manifest（24R: 起動フェーズ / 通常作業フェーズ分離）

Summary Manifest は、VALIS実行サイクルそのものの全文や実行ログを保持する場所ではない。  
VALIS実行サイクル再接続の定義本文は、VALIS Operation Definition を正とし、Flow Definition はその接続後の手順正本として扱う。

ただし、Summary Manifest は、Operation 核駆動の実行サイクルを実行可能にするため、**起動フェーズ** と **通常作業フェーズ** に関わる必要最小限の構造要約を保持できる。

```text
Summary Manifest が保持してよい起動フェーズ要約:
	Operation First Boot 済みかどうか
	完全起動済みかどうか
	3中核ファイルの標準配置パス
	起動フェーズで未解決の不足ファイルまたは版競合
	通常作業フェーズへ移行可能かどうか
	移行不可の場合の再開条件
```

```text
Summary Manifest が保持してよい通常作業フェーズ要約:
	対象ノードと対象層
	現在状態
	参照元
	処理フラグ要約
	未解決前提の要約
	前提フィードバック結果の要約
	承認ゲート要約
	次FLOW候補
```

```text
	テスト0: 起動前提確認の状態要約
```

### 12.18 出力時の VALIS / READ 表示

`VALIS` / `READ` / `TASK` / `INPUT` / `NEXT` は、利用者に対する運用表示であり、Summary Manifest の正式な状態管理そのものではない。

Summary Manifest は、`VALIS` 表示に必要な以下の要約を支えることができる。

```text
VALIS 表示を支える要約:
	VALIS 名
	VALIS 版
	現在の起動状態
	現在の層
	実行中または次候補の FLOW
```

Summary Manifest は、`READ` 表示に必要な以下の区分と起動段階差分を支えることができる。

```text
READ 表示区分:
	CORE:
		現在の起動段階または作業段階で、実際に読み込まれた中核定義ファイル。

		Operation First Boot 段階:
			- valis/core/VALIS Operation Definition.md

		完全起動後 / 通常作業段階:
			- valis/core/VALIS Operation Definition.md
			- valis/core/VALIS Summary Manifest.md
			- valis/core/VALIS Flow Definition.md

	OTHER:
		今回の作業で追加読み込みした Node File、実装ファイル、テストファイル、検証計画、検証証跡、作業計画、作業ログなど。
```

`READ: CORE` は、中核定義ファイルの利用可能性だけでなく、現在段階で実際に読み込まれた中核定義ファイルを示す。  
`READ: OTHER` は、今回の作業判断のために追加で読んだ非中核ファイルを示す。

Summary Manifest は、Operation First Boot 段階の `READ: CORE` が Operation Definition のみであることを許容する。  
Summary Manifest は、完全起動後または通常作業段階では3中核定義ファイルが `READ: CORE` に示されることを支えるが、読み込み失敗、欠落、版競合、未確認がある場合は、その未読ファイルを `READ` に出さず、`INPUT` または `NEXT` に不足前提として示す運用を支える。

Summary Manifest に、毎回の `READ` 出力全文や読み込みログ全文を蓄積してはならない。  
必要に応じて、作業結果照合、処理フラグ要約、次FLOW候補、Node File パス、実装ファイルパス、テストファイルパス、検証証跡IDとして必要最小限の構造要約のみを保持する。

実際に読み込んでいないファイルを `READ` に記載することは、作業結果照合の不一致として扱う。



### 12.17.6 起動テンプレート運用説明の保持範囲（26）

```text
	Operation First Boot 未成立
```

### 12.18.1 READ ルールの段階投入対応（20R）

Summary Manifest は、毎回の `READ` 出力全文を保存しない。  
ただし、段階投入型起動における `READ` 表示の正当性を支えるため、起動状態と未解決前提の要約を保持できる。

```text
Summary Manifest が保持できる段階要約:
	第0部:
		起動前提確認: 未実施 / 実施済み / 不足あり
		不足中核ファイル: あり / なし

	第1部:
		Operation First Boot: 未成立 / 成立 / 確認待ち

	第2部:
		完全起動: 未成立 / 成立 / 確認待ち

```

Summary Manifest は、存在確認だけのファイル、添付されただけのファイル、または配置予定だけのファイルを `READ` 済みとして保持しない。

`READ` の誤表示が発生した場合、Summary Manifest はその詳細ログではなく、必要に応じて「READ不一致あり」「未読中核あり」「再投入または再読込が必要」などの処理フラグ要約のみを保持する。

```text
Summary Manifest が出力前ゲートのために保持できる要約:

	Manifest 反映済みの構造要約

	承認待ちまたは承認済み状態の要約
	未解決前提、実体不一致、READ不一致、検証証跡不足の要約
	次FLOW候補または NEXT に影響する不足事項
```

```text
Summary Manifest に保持しない出力前ゲート関連情報:
	出力前ゲートの全文重複
	毎回の VALIS / READ / TASK / INPUT / NEXT 表示全文
	READ確認ログ全文
	内部推論過程
	詳細なファイル差分ログ
	出力前ゲートのチェックリスト全文
	一時的な表示修正だけで構造・状態に影響しない情報
```

出力前ゲートにより、Manifest 初期登録済み、Manifest 反映済み、検証済み、整合性確認済みと報告する場合、Summary Manifest にはその報告を支える必要最小限の構造要約が存在していなければならない。

出力前ゲートで不一致が見つかった場合、Summary Manifest には不一致の詳細ログを保存しない。  
ただし、不一致が後続 FLOW、承認状態、検証状態、Manifest 初期登録、Manifest 反映、または NEXT に影響する場合は、必要最小限の要約として保持できる。


### 12.18.3 Flow Definition 従属化の保持範囲

Flow Definition 従属化の定義本文は、VALIS Operation Definition および VALIS Flow Definition を正とする。  
Summary Manifest は、Flow Definition 従属化の全文、各 FLOW の詳細手順、毎回の前提フィードバックログ、または FLOW 実行契約の詳細ログを保持する場所ではない。

Summary Manifest は、Flow Definition が Operation Definition の制御下で使用されること、および後続 FLOW が参照すべき構造・状態・処理フラグ・NEXT に影響する要約のみを保持する。

```text
Summary Manifest が保持できる Flow Definition 従属化関連要約:
	Flow Definition が Operation Definition に従属して接続されること
	対象 FLOW が完全起動後にのみ実行可能であること
	前提フィードバック結果が FLOW 接続可否に影響すること
	承認ゲート、構造展開ゲート、出力前ゲートが FLOW 完了条件に影響すること
	FLOW 接続不可時の停止理由要約
	次FLOW候補または NEXT に影響する不足前提の要約
```

```text
Summary Manifest に保持しない Flow Definition 従属化関連情報:
	Operation Definition の全文重複
	Flow Definition の全文重複
	各 FLOW の詳細手順全文
	毎回の前提フィードバック過程全文
	FLOW 実行契約の詳細ログ全文
	出力前ゲートの詳細チェックリスト全文
```

Flow Definition 従属化により、Summary Manifest 上の次FLOW候補は、即時実行命令ではなく、Operation Definition の前提フィードバック、承認ゲート、FLOW実行契約を通過した場合に接続される候補として扱う。

### 12.17.7 3中核ファイル添付・配置ルールの保持範囲（27）

3中核ファイル添付・配置ルールの詳細本文は、VALIS Operation Definition を正とする。  
Summary Manifest は、添付・配置・読込の詳細ログ、全文比較ログ、起動テンプレート投入文全文、または中核ファイル本文そのものを保持しない。

Summary Manifest が保持できるのは、後続作業に必要な最小限の状態要約に限る。

```text
保持してよい要約:
	3中核ファイルの標準配置パス
	標準配置を利用できるかどうか
	暫定運用か正式運用か
	Operation Definition が読込済みか
	Summary Manifest が読込済みか
	Flow Definition が読込済みか
	正本競合の有無
	標準配置待ちかどうか
	完全起動済みかどうか
	次に必要な投入部または配置判断
```

Summary Manifest が保持してはならないものは以下である。

```text
保持しないもの:
	起動テンプレート本文全文
	第0部 / 第1部 / 第2部の投入文全文
	3中核ファイル本文全文
	添付ファイルと標準配置ファイルの全文比較ログ
	存在確認だけのファイルを読込済みとする記録
	配置予定だけのファイルを読込済みとする記録
	正本未確定のファイルを確定済みとする記録
```

添付済み、配置済み、読込済みは Summary 上でも区別する。  
存在確認または添付確認だけで `READ済み`、`完全起動済み`、`Flow接続可能` と要約してはならない。

正本競合、不足ファイル、標準配置待ち、または暫定運用がある場合、Summary Manifest はそれを未解決前提として要約し、後続の `INPUT` または `NEXT` に接続できる形で残す。

### 12.17.8 Manifest 層間接続ルールの保持範囲（28）

Summary Manifest は、A/B/C/D/E を単一ツリーとして保持しない。  
Summary Manifest は、層ごとのノード一覧と、層間接続を表す参照要約を保持する。

`parent_id` は同一層内の親子関係に限定する。  
A/B/C/D/E 間の接続は、`parent_id` ではなく `derived_from`、`implements`、`verifies`、`evidence_for`、`related_to` などの参照フィールドで表す。

```text
保持する基本規則:
	parent_id:
		同一層内の構造分解にのみ使用する。

	derived_from:
		上位仕様、由来、または制約元を示す。

	implements:
		実装対象となるB層またはA層要素を示す。

	verifies:
		検証対象となるB層またはC層要素を示す。

	evidence_for:
		証跡が紐づくD層検証計画または検証結果を示す。

	related_to:
		補助的関連を示す。
```

### 12.17.8.1 層ごとの接続要約

```text
A層:
	上位仕様・目的・要件。
	A内部の分解だけ parent_id を使用できる。

B層:
	機能・構成・振る舞い。
	B層トップノードは A層を parent_id に持たない。
	B層トップノードは A層を derived_from に持つ。

C層:
	実装設計。
	C層トップノードは B層を parent_id に持たない。
	C層ノードは B層を implements または derived_from に持つ。

D層:
	検証計画。
	D層トップノードは B/C層を parent_id に持たない。
	D層ノードは B/C層を verifies に持つ。

E層:
	検証証跡。
	E層トップノードは D層を parent_id に持たない。
	E層ノードは D層を evidence_for に持つ。
	必要に応じて B/C層を verifies に持つ。
```

### 12.17.8.2 推奨ノード要約形式

Summary Manifest がノード要約を保持する場合、必要に応じて以下の形式を用いる。

```text
Node summary:
	id:
	layer:
	parent_id:
	derived_from:
	implements:
	verifies:
	evidence_for:
	related_to:
	status:
	next:
```

すべての項目を常に埋める必要はない。  
ただし、層間接続が必要なノードについて、接続元・対象・証跡対象が未確定の場合は、未確定であることを要約し、完了済みとして扱わない。

### 12.17.8.3 浮遊ノードの扱い

以下は浮遊ノードまたは未接続ノードとして扱う。

```text
浮遊ノード候補:
	derived_from を持たないB層トップノード
	implements または derived_from を持たないC層トップノード
	verifies を持たないD層トップノード
	evidence_for を持たないE層トップノード
	異層ノードを parent_id に持つノード
	参照先が存在しないノード
	参照先の層種別が不整合なノード
```

浮遊ノードがある場合、Summary Manifest はそのノードを接続済み、反映済み、検証済み、または完了済みとして要約してはならない。  
必要に応じて、`未接続`、`上位参照元未確定`、`実装対象未確定`、`検証対象未確定`、`証跡対象未確定` などの状態を保持する。

### 12.17.8.4 保持しないもの

Summary Manifest は、層間接続ルールに関する以下を保持しない。

```text
保持しないもの:
	Operation Definition の層間接続ルール全文
	Flow Definition の詳細手順全文
	毎回のグラフ探索ログ全文
	親子関係の全展開ツリー
	参照解決の内部判断ログ全文
	存在しない参照先を補完した記録
```

Summary Manifest は、後続作業に必要な最小限の層間接続要約だけを保持する。
