# 観測記録容量/1・限定証跡

基点main 648bdd0 / 4.2.72。2026-10-23 UTC。契約: `design/specification/record-budget-v1.md`、計画: `operations/plans/record-budget-v1.md`。変更コードは `src/ecology/observations.js` のみ。Node/D9/E6の正式状態は草案を維持。

## 原因と反例

`baseline-counterexample.json`: 4000件の接触詳細を持つ小fixture、論理予算340,000 bytesで、旧実装は1T追加時に523,924 bytes必要と判定し、0Tの1行だけで停止した。前ターンの詳細を成功後に解放するため、解放予定を容量判定へ含めていなかった。

修正後、同予算・同詳細で8行を連続確定でき、最新の4000件と全ターン集計を保持する。解放は従来と同じ項目/時期だけとし、既存50T窓も維持。真の容量超過では既存行/ビン/系列を変更せず、拡張後に同じターンを追加できる。65行の境界/再試行と余裕予算の出力が一致した。

保存結果は、記録予算を拡張できる一方で読込側だけ256MiBの全文字列検査だった。読込の既定予算を1GiBへ整合し、ヘッダと行ごとの検査へ変更した。記録側はJSON長×4の概算、読込側はUTF16サイズであり、実ヒープ容量の測定ではない。

## 限定結果

- `record-budget.log`: 新規6件が成功。容量誤判定、拒否時の不変性、拡張後の系列一致、正確な読込境界、全文字列化しないこと、非有限値の拒否、有限の拡張上限。
- `observation-regression.log`: 既存12件が成功。1201行の合成履歴と過去の山、全期間CSV/保存復元、既存観測規則を含む。
- `archive-regression.log`: 既存5件が成功。全501行の合成履歴と保存復元、欠測/未知定義の拒否、保存失敗時の保持を含む。
- `browser/report.json`: Linux Chromium、実Worker、40×28/主24、実際の小容量記録器で6項目成功。0Tだけ初期行が入る容量まで拡張するfixtureを使い、次の実ターンで容量上限を発生させた。確定指紋/全行を保持して安全停止し、開始ボタンで拡張・再開し、実IndexedDBへ保存した結果を復元できた。例外0。

検査時のソース/テストSHAと実行範囲は `report.json`。Nodeはファイル別直接実行で各件の成功を確認した。

## 限界・後続

1GiBを実際に割り当てる試験、実生態の長期生存、全条件/全端末/Windows/配布/中断中の速度変更は実施していない。データや生態ターンの間引きは追加していない。容量は有限で、実上限到達やOS/IndexedDBの容量不足まで解消する保証ではない。長期グラフ描画/大量行配列展開/索引・キャッシュの保持量は後続の軽減確認へ残す。生態/グラフ配置/画像/保存スキーマは変更なし。
