# 初期と終盤で何が重くなるか

今回の結論は、**死骸だけではなく、学習済み情報・世界の複製・資源要求の組合せ・Worker転送・遠景描画が、それぞれ終盤の負荷を増やしている**ということ。

利用者の最新指示に従い、調査のみを確定する。途中まで着手した最適化試作はリポジトリ外へ退避し、製品コードは起点 `bb5d687` へ戻した。**今回のmain反映に最適化実装は含めない。** Core/A/B・Node/Project Summary Manifest・数値・素材・配置・製品4.2.77/生態署名219b2a50…は変更しない。計画は [実行範囲](../../plans/cell-late-runtime-v1.md)。

## 1. 条件と測り方

前工程の実フォームで作成した小40×28・主84体・河川・明示多層/淡水比較の1条件を用いた。初期値は `../cell-long-observation-v1/report.json` のconfigFile、終盤は同じ観察で保持したT500世界。**500Tを再走していない。** 初期T0→1は1回、終盤T500→501は別プロセス各1Tの2回の境界計時。これに初期/終盤各1TのV8サンプリングと呼出し数を追加した。

- 計算：[initial-before.json](initial-before.json)、[terminal-before-1.json](terminal-before-1.json)、[terminal-before-2.json](terminal-before-2.json)。`tests/cell-late-runtime-profile.cjs`。

## 3. 死骸以外の主因

### 学習済み情報と毎ターンの複製

生体全体は118.46MB。そのうち `informationState.learned` が**96.91MB（世界全体の約69.4%）**、自身の経験が8.20MB。個体内の学習を含む情報状態の反復確認が、受信・世界複製・転送を同時に重くしている。

特に重要なのは、主生物だけの学習ではない点である。

| 生体の表示グループ | レコード | 学習由来 | 学習JSON量 |
| --- | ---: | ---: | ---: |
| 植物 | 3,719 | 199,280 | 49.98MB |
| 分解者 | 2,518 | 157,984 | 43.15MB |
| 一次消費者 | 259 | 14,305 | 3.73MB |
| 主生物 | 7 | 223 | 0.054MB |

**主生物が7体に減っても、植物・分解者の情報だけで約93MB残る。** この条件では、下層生物が持つ学習情報とその複製/受信/転送の比重が大きい。これは表示グループ別の内訳で、情報の生態的役割分類を変更する判断ではない。

学習は1主体64由来の上限があり、T500では6,503主体中4,205主体が上限に達していた。期限切れの学習レコードは0、期限範囲はT501〜700。したがって、この断面は「期限切れデータを消し忘れた無限増加」とは言えない。**多くの生体が上限近くまで正規の学習を保持するため、合計が大きい。** 自身の移動履歴は合計6,935件、seenは0で、全生涯履歴の蓄積が主要因ではなかった。

`engine.beginTurn` の世界複製だけで **7.1ms → 平均1,121.4ms**。地形・前T観測等を複製対象から外す現行措置は存在するが、生体内学習・死骸は複製対象に残る。世界をWorker側、画面側、転送差分用の内部スナップショット等で持つ経路もある。実ヒープ容量や同時ピークは今回未測定であり、JSON値をそのまま実メモリ量とは呼ばない。

### 情報の受信処理

`informationBegin` は **7.7ms → 平均952.6ms**。各主体の既学習由来について有効期限/重複を確認し、近傍の環境・個体情報を候補化し、適用可能性・強度・受信済み内容を調べる。既にセル候補・内容の一時共有はあるが、受信者数と既学習数の増加に伴う走査が残る。V8サンプリングでも `informationReceive` が大きい。

### 資源要求と配分

要求総数は **643 → 112,661件（約175倍）**。要求主体は395 → 6,289主体で、単に生体が増える以上に候補が増えている。

| 終盤の要求 | 件数 |
| --- | ---: |
| 分解 | 102,316 |
| 無機養分 | 6,237 |
| 光合成 | 3,719 |
| 採食 | 389 |

分解要求の元を含む要求元は、死骸100,058件・有機物2,525件。**同じマスの分解者ごとに、そのマス内の各物質との組合せを作る**ため、死骸数の増加が要求列・共有プール・配分・確定移転の処理へ増幅する。遠隔取得や全マス総当たりではないが、局所内の候補の積が大きい。

`acquire` は **24.9ms → 平均1,644.2ms**。要求の検証/展開、同マス配分の反復、並べ替え、原料移転等を含む。V8の `allocate` と `acquire` も大きい。処理順・丸め・有限在庫の配分に関わるため、この場で省略してよい計算とは判定していない。

### 次ターンへの還元登録

`deferMaterial` の呼出しは **754 → 44,280回**、累計 **1.9ms → 平均246.6ms**。その都度、同T・同マス・同種の待ち物質を配列 `.find` で探す。待ち物質そのものは1,620件でも、登録の回数と探索が重なる。**蓄積量だけでなく、同じデータへの反復アクセスが重い箇所**である。これは配分/維持/分解等に内包される時間なので、それらへ加算しない。

### Worker転送

現行差分は行のトップレベル項目単位。個体の `informationState` 内の一部が変わると、その項目の全体を複製・転送する。学習の大半が不変でも巻き込まれる。

保持T500→501の3段階合計で、差分JSON換算 **236.75MB**、encoder約1,974ms、structuredClone約2,634ms、受信再構成約444ms。この別実験の合計は約5,052ms。実ブラウザのpostMessage全時間ではなく、通常の3段階用パケットを隔離して測った値。最速はfinalOnlyで経路が異なり、この3段階値をそのまま適用しない。

先行計算キューには最大6Tの上限がある。無制限キューとは確認していないが、大きなパケットを複数保持するため、ピークメモリとGCへの波及は追加確認の対象。

## 4. 死骸の残存と描画

T500死骸はJSON13.15MB。完全に空の死骸は**0件**。Eが0.001未満で正のものが14,189件、Mだけ残るものが10,363件ある。背景分解は小さな比率の切捨て、無機養分の還元先の容量、実在庫が残る間の保持に従う。単純な「空レコードを削除すれば済む」状態ではない。実物質や由来の扱いを変える判断は今回は行わない。

背景分解は **0.65ms → 平均258.5ms**。死骸/有機物をマスごとに集め、還元容量の配分と各在庫の減算・次T登録を行う。分解者の取得とは別に、背景でも残存物質を処理する。

実renderer、978×431の同寸法、動作/行動演出を切った3回の暖まった強制描画で比較した。

| 表示 | 初期 | 終盤 | 読み取れること |
| --- | ---: | ---: | --- |
| 遠景 | 平均2.23ms | 平均209.10ms | 全6,503生体と27,941死骸を対象。継続再描画が重い |
| 近景 | 平均0.80ms | 平均2.77ms | 可視範囲に絞られ、終盤は177生体/45死骸 |

遠景の死骸は、毎フレームすべての可視記号と斜線・ヒット領域を作る。既存の記号画像キャッシュはあるが、全死骸分の描画呼出しは残る。同一フレームで生体・地物・選択等も描くため、209msの全量を死骸だけの時間とは断定しない。

近景は初期/終盤それぞれの最初の主生物へフォーカスしたので、**場所は同一ではない**。初回や地形準備中は約164〜215msが掛かる別のコストがある。暖まった値を初回の応答性や全近景の保証には使わない。停止中の同一画面には既存の `drawIfChanged` 省略があり、常に209msを毎フレーム支払うという意味でもない。

## 5. 接触・観測・グラフ・一時データ

- 接触ペアは1,603 → 32,083、2.81MB。`engine.observation` が今Tの近傍接触から作り直し、前Tとの差で新規接触を判定する。全期間のペアが無制限に積み上がる構造ではないが、密集時の近傍組合せと終端集計は増える。CPUでは観測関数も確認されるが、前述の複製/配分/情報ほど大きい自己時間ではなかった。
- イベント5,872件・1.24MBと前T観測1.80MBは今Tの状態/結果。過去すべてのイベント列が世界へ累積する構造ではない。固定地形・鉱物資源数は主な肥大化対象ではなかった。
- 観測履歴は全Tを保持する一方、詳細情報の一部を1T/50Tで解放し、食性フレームは直近50件へ制限する。二分集約とseriesキャッシュも既存実装にある。したがって「全T記録だから直ちに全部重い/全部不要」とは言わない。
- グラフ再描画ではseriesの差分集計があっても、積上げ面の全点頂点・関係SVGの全Tパスを再構築する。T数に比例する負荷は残る。
- 保存済みの**実際の個体数履歴**を使い、現行 `paintStack` / `stackShape` をそのまま隔離した320×120の3回暖機描画は、全生物T0約0.20ms・T100約1.70ms・T500約3.13ms、主生物T500約1.30ms。今回500Tの個体数グラフ単体は、計算数秒・遠景209msに比べ小さい。構成グラフ/関係SVG/DOM全体も同じ速さという意味ではない。
- V8サンプリングでは終盤GCが約538ms観測された。大量の要求行・配列・Map・複製を作る実装と整合するが、サンプリング開始/停止の自己処理も含む観測窓であり、実アプリのGC比率やメモリリークをこれだけで確定しない。生態関数の内包時間と加算しない。
- `S.maps` の公開呼出しは初期21/終盤18回で、回数自体の肥大化ではない。1回が扱う主体/死骸の規模は増える。今回の主因を単に「索引を毎回作りすぎ」とは断定しない。

## 6. まだ断定できない範囲

現行世界にT0〜500の完全なEcoObservationsスナップショットは保持されていない。`turns.json` は各Tの主な生態要約と個体数であり、構成/関係の全観測行に代用していない。このため、実500T履歴を伴う `observations.append`・全構成グラフ・関係SVG・図鑑保存/CSV/IndexedDBの終盤コストは未実測。コード上の経路/上限と、実測済みの個体数グラフを分ける。

また、終盤でP/Qは0のため、寄生が多い別条件の処理はこの測定で評価できない。実アプリ全体のヒープ/GC、最大先行バッファ、長時間パン/ズーム/詳細/追跡の応答、Windows実機、異なるマップ・大盤面、T1000以降は未測定。これらを完了済みとは扱わない。

## 7. 後続への引継ぎ

今回確定したのは、**①個体内情報の規模と複製、②要求候補と配分、③還元の反復探索、④情報状態を含む転送、⑤遠景の残存物描画**が主要な負荷箇所であること。処理の削減方法・意味を変えてよい範囲・実施順は、調査結果をもとに利用者と別途議論する。マップ可視化は、その後の最適化・画面確認・安定化を経て扱う。

## 再計測する場合

保持終盤ファイルは134MiBのためGitには含めない。元世界のSHA256と上記指紋を照合してから使う。別世界を同じ結果として扱わない。初期/終盤CPU、状態規模、renderer、個体数グラフの計測器は記録作成に使用した。wire専用の現行のみの再計測器は、指示変更後に比較試作を含まない形へ整理したもので、この形では未実行。実装用の回帰テスト一式や500Tを再実行したという報告ではない。

```bash
node tests/cell-late-runtime-profile.cjs /path/to/retained-world.json /tmp/terminal.json terminal
node tests/cell-late-cpu-profile.cjs terminal /path/to/retained-world.json /tmp/cpu.json
node tests/cell-late-state-shape.cjs /path/to/retained-world.json /tmp/state.json
node tests/cell-late-wire-profile.cjs /path/to/retained-world.json /tmp/wire.json
node tests/cell-late-render-profile.cjs /path/to/retained-world.json /tmp/render.json
node tests/cell-late-graph-profile.cjs
```

rendererの比較fixtureだけは保持JSONを読み込むため `bypassCSP` を使う。製品のCSPは変更しない。CPUのtopSelf/topInclusiveはV8測定窓の集計であり、`post` などProfiler開始/停止自身のサンプルも含む。通常のターン計時と混ぜない。[source-hashes.json](source-hashes.json) に対象製品/調査器、[final-check.json](final-check.json) に今回の変更境界を記録する。
