参照元：

- `../gas-fizzbuzz-webapp/src/desktop/main.cjs`、`tools/package-windows.cjs`、`../.github/workflows/valis-windows.yml`：ローカル画面、Windows 配布、実 exe 検査の方式を参照。

- リポジトリ直下 `valis/core/`：Operation → Summary → Flow の役割に従って関連本文を再読。プロジェクト内の core は同一原文を配置する。

## 2. 機能・ルールの提案

- 同じ seed と設定なら、初期配置・種族特性・行動・ターン結果が再現する。seed は数値だけでなく明示的な入力として扱い、Math.random 依存を置き換える。
- FizzBuzz の「初期値→個体特性・環境」「読み込み→開始」の操作を参考に、初期集団を生成してから明示的に開始する。既存の20系統や画像は無断で複製しない。
- 添付の9種族・9行動・3戦闘モードを基礎にする。成長は年齢・世代・幼体から成体への段階で観測し、成体化と繁殖条件の具体式は草案仕様に明記する。
- 盤面、資源、個体の種族・年齢・HP・エネルギー・世代・血統、種族別個体数推移を表示する。開始、一時停止、再開、1ターン、再生成、速度変更を用意する。
- 全滅、単一勢力生存、上限ターンで区別して終了する。上限時の複数生存は「共存」であり、最多個体数を唯一の勝者と断定しない。
- 添付の初期配置重複、旧盤面と新盤面の二重状態、既に移動した個体の死亡反映、乱戦移動判定への lineage 欠落は、検査対象として明示し、結果の整合性を優先した更新方式へ設計し直す。
- 上限入力・分割実行・有界履歴で処理負荷を制御する。科学的な生態予測ではなく、ルールに基づくシミュレーションとして表示する。

上記提案はユーザー確認後に草案ノードへ展開した。現在の具体式は各Node Fileを正とする。成長・戦闘のバランスの最適性は確認済みとは扱わない。

## 5. 確認後の実行順序

1. 関連 core 本文を再読し、FLOW-01/03 の実行契約を確定する。
2. 確認された粒度で A/B/C 草案 Node File を作る。FLOW-07 で D 層検証計画を作る。
3. Project Summary Manifest を別ファイルで作成し、A/B/C/D を初期登録する。
4. 対応する C と D の存在・初期登録を確認してから src/ と tests/ を作成する。
5. エンジン単体、画面、Electron、Windows 配布を、それぞれ実行可能な環境で検査する。Windows 実機未実行なら未検証として残す。
6. FLOW-08 に従って、得られた結果だけ E 層へ記録。対象バージョン・ログ・有効条件を保存する。
7. 新規 E の初期登録と、既存登録項目の Manifest 反映を区別して行う。
8. 作業結果照合・出力前ゲートで実体と報告を照合する。全ノードは草案のまま、自己承認しない。
