# 実装前の最適化調査と適用順

調査版 `preimplementation-optimization/1`。基準main `e1e0e95`、製品4.2.32。利用者の「実装前に最適化できる部分を徹底的に洗い出す」を入力とする。計算・表示・通信等の改善候補34件と、追加生態モデルへ組み込む対策7件を整理した。**計41件は候補であり、全件実装を決定した一覧でも、速度向上を実測した結果でもない。**

## 1. 今回の実行契約と範囲

Operation Definitionを先行制御とし、プロジェクト内3coreの実行契約/記録分担/保持範囲/FLOW-12を実読する。既存4.2.31/32の仕様・計測、現行srcと通常実行の生成経路、採用済みの処理軽減/追加生態仕様を照合する。主FLOWはFLOW-12。調査結果・候補・適用順は本書、入口は現在ロードマップへ保存する。

今回は本書とロードマップだけを作成/更新する。A/B/C/D/E Node、Manifest、core、src/tests、画像、製品/配布物、正式状態、数値案の採否は変更しない。新Node/分割/Manifest初期登録は不要。既存構造・参照・状態を変えない調査/計画資料なのでManifest反映も不要。生存・性能・外観の新規合格は認定しない。

静的調査に加え、読取専用の `node tools/build-observation-model.cjs --check` を実行し、8優遇条件・22共有モジュール・生成物662,965 bytesの一致を確認した。新しい500T実行や性能比較はしていない。今回の照合は、根拠の所在、既対応との区別、参照先、候補の作用範囲、変更範囲に限定する。

## 2. 結論と既存の到達点

追加余地はある。優先するのは、**同じ世界を何度も索引化する処理、P/Qの全体検索、ターン受信から画面確定までのコピー/索引/描画、画像キャッシュミス**。既存グラフだけを軽くしても、大きな停止が解消する根拠はない。新生態の導入時に共通索引・所有権・キャッシュ寿命を決めると、後から各機能を作り直す範囲を減らせる。

以下は既対応であり、新規最適化として重複計上しない。

- table/1乱数表、固定地形キャッシュ、最良行動候補の線形選択、評価内の近傍/危険等のキャッシュ。
- 資源CAの有効近傍化、繁殖候補の疎集合化、Q探索索引の共有。ただし下表の残る走査は別。
- 3段階の差分通信、変更フィールド比較、適用先ID索引、最大6Tの先行上限。全変異の変更追跡は未実装。
- 静止時の再描画抑制、近景の個体/資源位置索引、背景の固定区画/部品合成、画像LRU、待機時の素材準備、事前陰影。
- 全ターン系列の追加分計算・対象キャッシュ、一部の50T集計増分化、CSV/JSONの8行単位Worker処理。出力全体を保持しない逐次ファイル書込とは異なる。

| N04 P0 | P/Q生活環・遺伝・抵抗 | H→P→Qの実在関係と所有者索引を同じレコードから参照し、表示用に別のP/Q世界を複製しない。宿主種×経路×段階の適合表は固定データ、相別費用は必要時更新。獲得抵抗/時計/感染窓は各主体で維持。 |

## 4. 採らない近道・後段でだけ比較する案

1. 個体数・ターン・生態作用・全期間原値を性能の都合で間引く、全下層や量機同居を一個体へまとめる方法は採らない。既採用の群落モデルは別。
2. 影を毎フレーム全体マスクへ戻す、近景の強制記号化、操作中の無断画質低下は採らない。明示した処理軽減設定とは区別する。
3. 少ない乱数を単純周期で使い回す/用途間で共有する方法は採らない。table/1の用途・個体・T・候補キーを維持し、描画/Worker順から独立させる。
4. GPU/WASM化は、境界や転送を減らした後にも残る特定の純計算へ限定して比較する。全体が速くなる保証はなく、倍精度/丸め/再現性/配布対応の費用が大きい。
5. 生態の複数Worker分割やSharedArrayBufferは後段候補。計算順・同じ資源/空き枠の競合・共有メモリ同期・配布条件を増やすため、現段階の先行策にはしない。独立した試験条件を並列実行する方法は別。
6. 全マップ×全生物×相×枝×年齢×性別×照明の全組合せを先に保存/準備しない。必要な不変部品と可視/近日必要状態を容量付きで準備する。

## 5. まとめて行う実装の順序

最適化を一件ずつ長期確認する必要はない。意味の同じ変更群でまとめ、現行最適化だけの同値比較と、新生態の挙動比較を分ける。

| 作業群 | まとめるもの | 次へ渡す確認 |
| --- | --- | --- |
| 1 共通基盤 | C10、C01、N01〜N05、M01の更新口設計 | 生成経路・処理境界・所有権・同居予約を明示。実装中は既存比較器/索引との一致を併用。C/Dは既存責務へ接続し、新分割が必要な場合だけ事前提示 |
| 2 計算の無駄削減 | C02〜C07、R01、R02、M04、M07前半 | 低競争/混合/密集/寄生多の短期比較。旧規則での世界・全原値・乱数/調停・収支一致。新生態の意図的な差とは分ける |

## 6. 効果の確認方法と未確認事項

- **生態計算/画面確定/描画/GC/通信/出力を別に測る。** 平均だけでなくp95/p99/最大値、50/100/250ms超の回数、操作応答を記録。既存の入れ子計測を足して寄与率を作らない。UIスレッドとWorkerのプロファイルを分ける。
- 小中大・遠近、初回/定常、疎/密集、寄生多、100/300/500Tを代表条件にし、同じ世界・表示寸法・DPR・設定で比較する。全件組合せの総当たりはしない。
- 転送bytes/変更ID数/clone量/索引再構築回数/キャッシュhitとmiss/画像作業回数/生きたWorker数を測り、原因に対応した指標で評価する。NodeのメモリだけでCanvas/GPUを測った扱いにしない。
- 新世界→観測→停止再開→結果→保存/再生→新世界を繰り返し、旧世界の参照/画像/Workerが増え続けないかを確認する。明示保存済みデータを解放対象へ入れない。
- 最適化だけの変更は、同じ世界指紋/全ターン原値/有限収支/処理順/同点/乱数と、影響箇所の描画/操作を照合。新仕様の導入は旧結果との完全一致を要求せず、新規則の境界と再現性を確認する。
- 性能目標は既定の500Tで5〜15分・準備60秒以内を維持する。個々の処理の高速化と、表示テンポを保った総プレイ時間は区別する。応答/フレームの比較目標は測定環境を明記し、全PC保証にしない。

今回、改善倍率/総削減率を断定できる新計測はない。局所が2倍になっても全体が2倍になるとは限らず、各候補の効果は加算できない。まず作業群1〜3を新機能と共通化し、対象箇所の実測で作業群4を選ぶ。利用者が改めて決める必要がある仕様変更は今回見つかっていない。大きな画風変更・生態省略・乱数方式変更が必要になった場合は、最適化として黙って採用せず具体案を戻す。
